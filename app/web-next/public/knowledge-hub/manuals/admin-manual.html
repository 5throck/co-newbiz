관리자 매뉴얼 — 시스템 관리자

언어: English · 한국어

독자: 시스템 관리자(리뷰 프로세스의 투자위원회 "administrator"와 다른 개념 — 여기서는 기술적 시스템 관리를 뜻한다) 대상 아님: analyst(business-manual.md 참조), 배치/백업 파이프라인을 일상적으로 운영하는 운영자(operations-manual.md 참조)

이 매뉴얼이 다루는 것

계정 관리, 규제 버전 관리, 마스터 데이터 관리, 알림 rule 설정 — Stage 5에서 관리 콘솔이 만들어지면 그 콘솔이 담당하는 업무.

1. 계정 관리

  • 셀프 등록 → pending → 관리자 승인 → active. 역할: admin / analyst / viewer.
  • 비밀번호 초기화: 사용자가 요청 → 관리자가 임시 비밀번호 설정 → 사용자의 다음 로그인은 다른 어떤 작업보다 먼저 비밀번호 변경 화면을 강제한다(must_change_password) → 새 비밀번호는 password_history와 대조해 재사용을 차단한다.
  • 관리자는 사용자의 실제 비밀번호를 절대 볼 수 없다 — 해싱은 단방향이다(PBKDF2-HMAC-SHA256, 210,000회 반복, 워크스페이스에서 재사용한 scripts/lib/auth.ts 기준).

2. 접근 제어 — 관리자가 몸에 새겨야 할 단 하나의 규칙

admin 역할은 딜 데이터에 대한 자동 접근권을 부여하지 않는다. 시스템 관리 권한과 딜 조회 권한은 별개다(design 8.10절, 미팅 M7-1). 특정 프로젝트의 데이터를 보려면 관리자도 다른 사용자와 마찬가지로 명시적인 project_member grant가 필요하다 — 그 grant 자체도 감사 로그에 남는다. 자신이 멤버가 아닌 프로젝트를 "그냥 확인"하고 싶어지는 순간이 바로 이 규칙이 막으려는 경우다.

3. 규제 및 절차 버전 관리

  • 진행 중 프로젝트 전반의 project_policy_pin 상태 조회.
  • 개정이 발효되기 전에 policy_change 영향분석 기록을 검토.
  • 기록된 policy_change 결정 없이 프로젝트가 고정(pin)한 정책 버전을 수동으로 덮어쓰지 말 것 — 이 메커니즘이 규제 개정이 진행 중 프로젝트의 RAG 등급을 소리 없이 뒤집는 것을 막는다.

4. 마스터 데이터 관리

  • staging_unmapped 큐 처리 — 매핑되지 않은 산업/회사/단위 코드는 여기서 격리되며 자동 생성되지 않는다.
  • 지역·산업 프로필 필드에는 source/verified_on/maintainer 메타데이터가 필수다. _validate.ts는 출처 없는 필드를 거부한다. 프로필을 정정하는 관리자는 값만이 아니라 이 메타데이터도 함께 제공해야 한다.

5. 알림 및 RAG rule 관리

  • RAG 임계값과 히스테리시스 밴드(design 8.2절, 미팅 M3)는 하드코딩이 아니라 설정이다 — 다만 변경에는 즉석 관리자 수정이 아니라 트리거 목록에 따른 ADR이 필요하다.
  • 알림 채널 설정, 쿨다운/히스테리시스 파라미터(미팅 M7의 24시간/7일 기본값).

6. 데이터 소스 관리

API 키는 절대 표시되지 않는다 — 관리 콘솔은 키 값이 아니라 존재 여부와 최종 성공 시각만 보여준다. UI 취향의 문제가 아니라 확정 규칙이다(design 4.9절).

7. 로그와 감사

  • 감사 로그는 append-only — 관리자라도 항목을 삭제할 수 없다. 보존/아카이빙이 유일하게 허용된 수명주기 조치다.
  • 컴플라이언스 리포팅용 CSV 내보내기를 제공한다.

8. 관련 문서

  • docs/governance-operations.md — waiver 및 해석 운영(compliance-officer의 도메인. 이 매뉴얼의 시스템 관리 범위와 인접하지만 별개다).
