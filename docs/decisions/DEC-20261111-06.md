## Context

- PM dispatched this Row 0 under the Design Gate (ADR-0074) after the target-identity defect
  chain was diagnosed at S6/S7 brownfield: LLM candidate suggestions arrive without a DART
  corp code, get registered under paren-glossed display names with NULL codes, and every
  identity join downstream — corp-code resolution, DART financial sync, duplicate handling,
  the PATCH repair path — then fails in a different way. All eight diagnosis claims were
  re-verified at `main @ fb729a51` before this ruling (design §2, with file:line).
- The live dev DB carries the incident: a md_company row named `한전KPS(KEPCO KPS)` holding
  corp code 00159193, which the corp-code cache proves is `한국전력공사` — a different company —
  while a second, clean `한전KPS` row (00159218, 40 fact rows) already exists; three sibling
  targets (`파워(Power)`, `비에이치아이(BHI)`, `태웅(Taeung)`) sit with NULL codes.

## Determination

1. **R1 — canonical names at every identity write boundary.** `canonicalCompanyName` (new
   pure module) strips trailing parenthetical glosses and leading corporate-form markers;
   both `md_company.name_ko` and `brownfield_target.company_name` hold the canonical form;
   `resolveOrCreateCompany` gains a raw-name second pass that normalizes legacy rows in
   place. The gloss survives on the proposal card, in the evidence trail, and in DART's own
   corp_name.
2. **R2 — server-side enrichment, exact-unique only.** Suggestions are enriched from the
   deterministic cache against the canonical name; a code attaches only on an exact and
   unique name hit (`태웅`'s five-way cache ambiguity attaches nothing). The model may supply
   an optional `dart_corp_name` — never the code. Enrichment never fails the response.
3. **R3 — code-aware dedupe, idempotent registration.** Both POST routes match on code or
   canonical name and return 200 with the existing row (`deduped: true`); PATCH collisions
   return 409 with `existing_target_id`; no auto-merge.
4. **R4 — one PATCH path.** `updateTargetFields` canonicalizes, updates, always re-links the
   company master, audits uniformly; both PATCH routes delegate; explicit null clears a code.
5. **R5 — corp-code authority with visible mismatch (the safety-boundary ruling).** The
   name-based validation/resolution chain — not the user-entered code — is the demonstrated
   hazard: it silently persisted wrong codes via first-partial-hit name search and deadlocked
   with zero facts. The expect-name is canonicalized first; on remaining containment failure
   the entered/stored code wins, the mismatch (with DART's registered name) is warned and
   banner-surfaced, and the name-search downgrade is removed whenever a code exists; the
   no-code path resolves only on exact-verified hits.
6. **R6 — failure visibility.** Auto-sync errors surface as banner state with retry; the
   sync route audits `company_financial_sync_failed`; the eval-draft advice becomes
   conditional on the target's code (honest limitation: the DartSyncError code rides the
   response envelope — `audit_log` has no metadata column, per the DEC-20261111-05
   precedent).
7. **R7 — `고유번호 미확인` chip** on suggestion cards without a code.
8. **R8 — data repair is out of code.** Post-merge owner actions through the fixed PATCH:
   `비에이치아이(BHI)` → 00409788 (unique, confirmed); `태웅` → owner picks among FIVE exact cache
   rows (the dispatch's 00216267 suggestion is unconfirmed — the listed `태웅`, stock 044490,
   is 00186799); `파워(Power)` → owner confirms `파워로직스` (00269612) or another entity;
   `한전KPS(KEPCO KPS)` → PATCH 00159218 links to the existing clean master row; the orphaned
   wrong-code row (0 facts) is renamed to `한국전력공사` or deleted by owner decision.
