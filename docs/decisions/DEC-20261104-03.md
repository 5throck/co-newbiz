## Context

- Design 2026-08-31-pipeline-execution-environment §2.5 records that three of the
  repo's four `.env` readers parse values themselves and all three disagree with the
  dotenv 16.3.1 parser Next.js runs as the server: Next strips an inline `# comment`
  after a value, the other three did not.
- The divergence was measured on 2026-11-04: with
  `CO_NEWBIZ_LLM_PROVIDER=custom  # openai-compatible | anthropic | gemini | custom | none`
  on disk, the root-env path set a 64-character value while the dotenv path set
  `custom`. `llm.ts` compares the string only against emptiness and `"none"`, so the
  64-character form entered provider selection as a configured-but-unmatched provider —
  `isLlmConfigured()` true, dispatch silently inert. The value on disk was corrected,
  the parser divergence was not.
- The Design Gate was asked for one row: the shared parser. A second, adjacent finding
  (`scripts/lib/env-keys.ts:18`'s `[A-Z_]+` key charset makes keys containing digits
  unreachable) surfaced during review of the same lines.

## Determination

- **Row 0 — approved and implemented**: `scripts/lib/env-value.ts` exports
  `parseEnvValue(raw: string, keyName?: string): string` with dotenv's `#` semantics
  (trim; `"`/`'`/backtick quoted values closed by the matching quote with `#` literal
  inside; unquoted values cut at the first `#`; escaping not implemented). A cut value
  warns once, naming the key and never the value. `scripts/lib/env-keys.ts:35`,
  `app/web-next/lib/root-env.ts:53` and `app/web-next/prisma.config.ts:17` call it in
  place of their own value handling. A
  test seam (`resetPipelineKeysForTests`) is added to env-keys.ts because the loader
  had no reset and therefore no test.
- **Row 1 — authorised, deferred, explicitly excluded**: the key-charset limitation in
  `scripts/lib/env-keys.ts:18` is a real defect (a key such as `DART_API_KEY_V2` never
  matches) but is not part of this change. It is filed as its own future ticket. It was
  excluded because it is a different defect class from value parsing, no key on disk
  needs it today, and the §4 verification design (three cases per loader) is evidence
  for the parser change only.
- **prisma.config.ts included despite being a behaviour change**: its previous
  `/^([A-Z_]+)="?([^"\n]*)"?$/` could not express a quoted value at all and did not
  trim, so routing it moves behaviour as well as shape. Admitted because no value on
  disk is quoted, and because leaving it out would keep a fourth divergent parser that
  `prisma db pull` reads. Widening the match surface from `[A-Z_]+` to `[A-Z_0-9]+` and
  from `[^"\n]*` to `.*` also newly admits numeric-suffixed keys and quote-containing
  lines into that loader's unconditional overwrite path — it has no `=== undefined`
  guard, unlike the other two readers — and neither shape exists on disk today.

## Consequences

- The 2026-11-04 divergence now fails before the change and passes after it, in all
  three loaders (`tests/unit/root-env.test.ts`,
  `tests/unit/env-keys.test.ts`, `tests/unit/prisma-env-loader.test.ts`).
- A value that must contain a literal `#` now has to be quoted. This is dotenv's rule
  copied deliberately, not a new restriction; §2.5 states it so no one rediscovers it
  as a bug.
- The key charset stays as each reader has it (`[A-Z_0-9]`-style in root-env.ts and
  prisma.config.ts; `[A-Z_]+` with no digits at `scripts/lib/env-keys.ts:18`, which is
  the deferred Row 1 defect) until Row 1 is scheduled.
