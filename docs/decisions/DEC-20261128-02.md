## Context

- Historical-variant rows currently carry an adopt button (`BusinessCaseStage.tsx:1848` —
  `{!c.adopted && <button … onClick={() => adopt(c.id, c.scenario, c.variant)}>}`) and
  `adoptBusinessCase` has no variant restriction (`business-case.ts:509-537` — it checks track,
  target selection and shortlist status, never `variant`).
- ADR-0117 §2: "The gate judges market_forward only … the historical variant is comparison
  evidence and can never become the recommendation." Adoption is the recorded human decision
  that names the case feeding the fs gate and S10/S11 (`process/flow.spec.yaml:1001`) — an
  adopted historical row would point the gate basis at the comparison-only variant.

## Existing-data compatibility check (read-only, 2026-11-28)

Adoption records are `process_run` rows with `stage = 's8_case_adopt'` whose `meta_json`
carries `model_id` (`business-case.ts:563-581`). Compatibility query pattern:

```sql
SELECT pr.id, pr.project_id, pr.started_at, COALESCE(m.variant,'market_forward') AS variant
FROM process_run pr
JOIN business_case_model m ON m.id = json_extract(pr.meta_json, '$.model_id')
WHERE pr.stage = 's8_case_adopt' AND COALESCE(m.variant,'market_forward') = 'historical';
```

Read-only scan of the dev database (`db/data/co-newbiz.sqlite`, 2026-11-28): 3 adoption
records exist, 24 historical-variant models exist, **0 adoptions point at a historical-variant
model**. No compat migration is needed — the guard is forward-only, and no recorded human
decision is affected. (Non-interactive environments should re-run the same query before
shipping; the guard itself must tolerate a pre-existing historical adoption gracefully — see
the design addendum's compat note.)

## Ruling

Restrict adoption to market_forward, per frontmatter `decision`. The guard is a write-time
rejection in the same family as the existing ADR-0143/ADR-0158 rejections (archived model,
target-mismatch), and the UI hides the affordance on historical rows — defense in depth, with
the 409 keeping direct API calls precise. Boundary #2 is unchanged: adoption still happens only
through a human's explicit click.

## Consequences

- No schema change, no migration; no existing adoption records to repair (dev scan above).
- Historical rows keep their full comparison role in the scenario table and the IC-package
  `comparison` block (ADR-0117 §4) — only the adopt affordance changes.
- The latent regeneration duplication on historical rows closes together with the
  market_forward path fixed by DEC-20261128-01.
