## Context

A regeneration was expected to fully supersede the previous round. It does not. Verified root
cause (investigator's report, citations re-verified in source 2026-11-28):

1. `archiveSupersededRound` (`app/web-next/lib/business-case-cleanup.ts:79-102`) archives the
   previous round at the start of every generate run, but line 95 skips any model a decision
   record still names: `if (isModelReferenced(db, projectId, m.id)) continue; // adopted /
   gate-referenced: leave as-is` (`isModelReferenced` at :38-53 — adoption `s8_case_adopt`
   process_run meta, gate rationale text, gate evidence/criteria blobs).
2. The fresh round bare-INSERTs new `business_case_model` rows
   (`business-case-generator.ts:2465-2478`); `db/migrations/0044_business_case_model.sql` has no
   unique key on (project, variant, scenario, target). Result: the adopted old-round row stays
   ACTIVE beside the fresh rows — duplicate active rows for the same scenario.
3. The S8 header adoption chip keys on `cases.find` over the active list
   (`app/web-next/components/stages/BusinessCaseStage.tsx:1556`), so with duplicates the chip
   lands on an arbitrary round's row and the human's adoption stops being visibly attached to
   the adopted case.
4. S9+ downstream readers resolve the adoption record directly and keep consuming old-round
   numbers with no staleness signal: `greenfield-execution.ts:151` (`adoptedCaseCapex`),
   `covenant-dscr.ts:296` (`adoptedCfads`), `investment-simulation-s8.ts:104` (adopted-note
   lookup), `process-flow.ts:1005` (S8 completion keys on the latest active market_forward
   model).
5. Dev-database evidence (read-only scan of `db/data/co-newbiz.sqlite`, 2026-11-28): 3
   (project, scenario) pairs currently hold >1 active market_forward valuation model; 34 models
   are archived and none of them is referenced by any adoption or gate record — the exact
   fingerprint of the keep-active skip (referenced rows can never be archived, so the archived
   set is by construction unreferenced).

The skip was introduced by the 2026-10-16 round-archive fix (commit `95153be4`, PR #598,
CHANGELOG 2026-10-16) and is pinned as correct behavior by
`tests/unit/business-case-round-archival.test.ts:139-173` ("adopted and gate-referenced models
survive"). That pin must be rewritten as part of the implementation.

## Ruling

Supersede-to-archive + stale-adoption + manual re-adoption, per frontmatter `decision`:

- **Archive referenced models on the supersession path** — the `continue` at
  `business-case-cleanup.ts:95` is dropped for `archiveSupersededRound` ONLY.
  `cleanupLegacyModels` (the ADR-0158 human-only legacy cleanup) keeps its delete-vs-archive
  protection untouched.
- **Derive staleness, never alter records** — new `StaleReason` value `"adopted_superseded"`
  when the latest adoption's model is archived, flowing through the existing ADR-0206 helpers
  (`staleS8Records` / `buildS8Staleness` / `resolveS8Staleness`, `business-case.ts:225-301`,
  readers pinned by `tests/unit/s8-stale-adoption-readers.test.ts`) so the banner, the fs GO
  block and the downstream readers pick it up with no new plumbing.
- **Manual re-adoption is the recovery path** — the adoption record is never re-pointed by
  code. Generation remains proposals-only (ADR-0098 boundary #2; `flow.spec.yaml:1001` records
  the adopted case as a human decision feeding S10/S11).
- **Header chip keys on the adoption record** — display follows
  `latestAdoption.modelId` (resolving through `findAdoptedCase`'s archived fallback,
  `business-case.ts:450-455`), not `cases.find`.

## Reversed decision

This ruling **reverses the 2026-10-16 keep-adopted-active decision** (commit `95153be4`, PR
#598). The reversal is justified because the thing keep-active was protecting — the adoption /
IC audit trail staying resolvable — is exactly what ADR-0158's archive mechanism (2026-10-09,
Accepted) already preserves: archived models stay resolvable by id for the adoption and
IC-package history views (`findAdoptedCase` falls back to the archived set), and ADR-0117's
gate-judges-market_forward rule reads the adoption record, not the active list. Keep-active
therefore has no remaining benefit and two standing costs: duplicate active rounds, and stale
downstream consumption with no signal.

## Consequences

- After the fix, every regeneration leaves exactly one active round (the fresh one). The three
  existing duplicate pairs in dev data heal on the project's next regeneration (all superseded
  rounds archive in one pass); no backfill migration (ADR-0158 grandfathering precedent).
- A project whose adoption was archived by a regeneration shows the stale banner and cannot
  record an fs GO until a human re-adopts — the same recovery UX ADR-0206 established for
  excluded targets. The record itself is untouched (byte-identical), and the adopted case's
  figures stay resolvable in history views.
- Downstream readers (greenfield-execution, covenant-dscr, investment-simulation-s8,
  process-flow) surface the stale state instead of old-round figures via the existing
  staleness plumbing.
