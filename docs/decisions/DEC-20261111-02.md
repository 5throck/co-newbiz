## Determination

1. **Batch ruling — approve D1–D8 as designed.** The design doc is the single elaboration of
   record; per-item scope, files touched, and test plans are §3–§10 there.
2. **SR2/SR3 minimal-vs-schema scope split (binding).** This batch ships the no-schema-change
   forms only: `login_failed` auditing via the FK-free `audit_log` columns, and rightmost-XFF
   throttle keying over the existing in-memory bounded map. The schema-level upgrade — IP and
   user-agent columns on the audit trail and a durable (survives-restart) throttle store shared by
   the login and register throttles — is committed to a **follow-up ADR item** and must not be
   smuggled into Rows 1+. In-memory throttle reset on restart is accepted risk for now, recorded in
   the design (§6) and the follow-up list (§13.1).
3. **B-3 honesty rule (binding).** On the deal board, kill-criteria evaluation state is rendered in
   exactly three visible states: triggered / evaluated-false / unassessed. `unassessed` NEVER
   renders as pass — never green, never a silence that reads as clean; an empty ledger renders a
   non-claim dash. This rule outlives this batch: any future board or KPI surface showing kill
   evaluation inherits it (same doctrine as ADR-0049 at read time and the gate-ack "silence is
   never read as pass" rule).
4. **B-6 check-only-if-trivial mandate (applied).** (a) and (b) verified legible in code — no fix
   shipped; (c) verified absent and recorded as follow-up, not built in this batch. The one
   cosmetic candidate found (catalog hard-block text not used for all `KNOWN_HARD_BLOCKS` in the
   decision-panel error path) is logged as follow-up §13.3, explicitly not blocking.
5. **Source-doc recovery follow-up (mandatory, non-blocking for this Row 0).** Recover or
   regenerate the improvement-plan and admin-account-review documents and reconcile them against
   design §2 before the next plan-driven batch; recover or re-issue DEC-20261111-01.

## Consequences

- Rows 1+ implement D1–D7 (D8 ships no code) under separate dispatch; the security items (D1–D4)
  need security-engineer review at the AI-2nd stage before the human gate.
- The audit trail gains `login_failed` rows for every failed attempt — audit volume grows (one row
  per failed login); the audit-log admin surface shows the new action without schema change.
- The flat stage routes gain a first server-rendered redirect path; the CarrierGate client surface
  shrinks to picker + fallback duties with its exported name stable.
- Follow-up load: one ADR item (audit/throttle schema upgrade), one UI follow-up (tranche-conditions
  read-only view), one cosmetic alignment, and the source-doc recovery — all recorded in design §13.
