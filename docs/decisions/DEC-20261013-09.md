## Approver

- **Approved by**: the human decider (user, account techcross), by chat instruction on 2026-10-13 relayed by the PM, asking platform-lead to implement the platform-lead-owned deviations listed in the ADR-0165 acceptance record (DEC-20261013-07). ADR-0165's status is not changed by this record; the addendum there describes the implementation.

## What was decided

1. **Notifications (deviation 1).** New `notification.trigger_type` values `establishment_step_reopened` and `establishment_step_assigned`; additive `dedupe_key` with a per-recipient partial UNIQUE index. Recipients: project lead(s) and the reopened step's assignee for a reopen, the new assignee for an assignment; the actor is never notified; a cascade reopen is one notification per recipient.
2. **Server field (deviation 2).** `reopened_after_gate` is computed once in `lib/establishment.ts` and consumed by the establishment read, the IC package, process-flow and both UI surfaces. A reopen never revokes a gate decision; the flag only makes the gap visible.
3. **Call path (deviation 3, first half).** `entity_establishment_step_event.via` in `ui | api | mcp | unknown`, and the audit target suffix `@<via>`.
4. **Human-only on REST (deviation 3, second half).** Finding: bearer tokens could call the REST mutations directly. The route-level guard `humanOnlyDenied` (existing convention) now returns 403 `human_only` for completing a step, assigning and reopening.

## Basis and limits

- Migration 0141 rebuilds `notification` because SQLite cannot alter a CHECK constraint; the header carries a rollback block and `@reversible: true` (ADR-0014, ADR-0163). Notifications of the two new types are deleted by the rollback.
- The scenario test `tests/scenarios/greenfield.test.ts` still looks for the pre-ADR-0165 button text and fails independently of this change; it needs its own update.
