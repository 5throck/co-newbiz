## Basis and limits

- **(a) Design Gate determination.** The i18n work is ruled **not exempt** (no E1–E5 code applies): it adopts a framework, creates new modules (`app/web-next/i18n/*`, catalogs, lint/parity tests), and changes a cross-cutting convention across the app. The design doc `docs/designs/2026-10-23-i18n-ui-adoption-design.md` is written and registered via `scripts/spec-register.ts` (source: manual, status: implemented) as spec `2026-10-23-i18n-ui-adoption-design`.
- **(b) ko-master governance deviation ruling.** The workspace `i18n-locale-config` skill (line 129) sets en as the default/master locale of its 16-locale baseline. This project rules **ko** the master: `ko.json` is the source-of-truth catalog, and a missing `en.json` key falls back to ko (fail closed toward the primary audience), never to a raw key. The deviation is deliberate, recorded in ADR-0184 and this record, and reversible only by a new decision record — not by a silent catalog flip. Everything else in the skill's baseline (the 16 canonical BCP 47 tags) is adopted as-is.
- **(c) Approval scope.** The user's plan approval on 2026-10-23 constitutes the design approval for the three transcribed decisions (locales, ko master, cookie negotiation) and the design doc's architecture; it is the Row 0 record for this change set. Implementation rows (T1–T6) must cite the design-of-record §6 and re-verify the tree if it has moved.
- **Limits.** The approval covers UI chrome localization only. Document/wiki/PDF/email body translation, DB `name_ko` schema changes, translations beyond ko/en, and ja/zh fonts are out of scope by the approved plan; ADR-0108's remaining decisions (documentation surface) are untouched by the partial supersession in ADR-0184.
