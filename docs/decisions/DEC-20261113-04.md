alternatives: >-
  (1) Ignore-once-never-return (threshold 1): rejected — the user stated the threshold explicitly ('2 or more times'); one accidental click must not permanently silence a candidate. (2) Boolean ignore flag / upsert row per (opportunity, company) with an ignored_at stamp: rejected — the user's rule is a COUNT of ignore events; a flag cannot represent 'ignored twice' and cannot express the 1-ignored state the count chip needs; an upsert would also need an UPDATE path on an audit-style record. (3) Suppress on fuzzy similarity (isSimilar) instead of exact key: rejected for suppression — isSimilar's substring and token-Jaccard matching is right for dedup (keep the NEWEST name out of a list) but wrong for exclusion (silence a candidate forever): 'Samsung' would suppress 'Samsung Electronics' (company names romanized from the Korean examples). Existing-name dedup keeps isSimilar; ignore suppression uses exact keys. (4) Suppress per-user (ignored_by in the match): rejected — proposals are shared deal-flow artifacts; one analyst ignoring a company silences it for the whole opportunity review (consistency beats personal preference; the table still records who for audit). (5) Global (workspace-wide) suppression: rejected — market scope differs across opportunities; a company irrelevant to deal A may be core to deal B. (6) Filter inside the LLM prompt only (no post-extraction filter): rejected — prompt hints are advisory; the model can still emit an excluded name, and the requirement is a hard guarantee. (8) Client-only suppression (localStorage ignore list): rejected — per-device state breaks the guarantee on any other device/session, leaves no audit trail, and cannot inform server-side generation.

## Context

- Brownfield S6/S7 candidate discovery (web-search candidate proposal — Korean copy, translated) regenerates proposals on demand. The
  ignore button on a web-search proposal card (`DiscoveryPanels.tsx:149-158`, i18n key
  `tc("ignore")` at `:157`) only filters the in-memory `webProposals` array — nothing is
  persisted, so the ignored company reappears on the next generation. Verified on the working
  tree, 2026-11-13.
- The user ruled (PM relay, 2026-11-13): a company ignored **2 or more times** must not reappear
  in future web-search proposals.
- Every file:line claim in the dispatch brief was re-verified by the dispatched agent; two
  corrections to the brief's assumed state: (a) the LLM proposal paths do NOT use a bare
  `includes` check — they already filter via `isSimilar` (`name-similarity.ts`); the bare exact
  match exists only in `synthesisFallback` (web-search route `:80`) and the master-proposals GET
  (`target-proposals/route.ts:60`); (b) a canonicalization helper already exists
  (`canonicalCompanyName`, `company-name.ts`, design 2026-11-11-target-identity-resolution §D1)
  and is the right base for the ignore key, extended with a stock-company-word/㈜ token strip (the Korean stock-company word — Korean copy, translated; matched as a literal by the implementation).
- Knowledge anchors (annotations moved here for the validator's bare-path contract):
  ADR-0012 (audit log is append-only) is the append-only precedent the ignore event store
  follows; ADR-0074 (process meta-model) is the Design Gate this Row 0 determination runs
  under; ADR-0118 (stage-scoped LLM decision support) owns the web-search proposal contract
  the suppression composes after, unchanged.

## Determination

1. **Row 0: non-exempt.** Schema change + new audited route + multi-surface suppression + UI
   changes are architectural; the full Design Gate chain applies.
2. **Rulings 1–7 adopted** as specified in the decision line; the design doc is the
   specification of record. Threshold constant 2; exact-key suppression; per-opportunity scope;
   both proposal surfaces filtered; existing-name filter hardened in the same change.
3. **Spec registration deferred to landing** — another in-flight batch owns
   `docs/specs/registry.json` right now; PM runs `bun scripts/spec-register.ts --file
   docs/designs/2026-11-13-proposal-ignore-suppression-design.md --source manual --status
   implemented` (or draft, per landing state) at merge time. The design doc's frontmatter records
   this explicitly.

## Conditions

- Implementation follows the design doc's touched files, test plan, and openapi registration
  (drift gate) in the same PR.
- The migration is `0192_target_proposal_ignore.sql`, `@reversible: true`, purely additive; the
  ignore table gains no delete or update path in application code.
- The count chip shows count by text (not color alone); locale keys land in en.json and ko.json.
- If implementation reveals the stock-company-word strip heuristic (the Korean legal-form word — Korean copy, translated) misfires on a real name, the fallback
  is to key on `canonicalCompanyName` + `normalizeName` only (no token strip) and record the
  discrepancy — never to widen suppression to fuzzy matching.
