# Brownfield 필요 역량 검증 — S9 capability-dd 설계 (Proposed)

- **일자**: 2026-10-19
- **상태**: Implemented (2026-10-19 — §3.1/§3.2 판정 탭·저장·라우트, §3.4 카운트 요약; §3.3 교차검증은 decider 결정으로 제거. 2026-10-17 S9 정비 2차 — 판정 주전장을 S8에서 S9 필요 역량 검증 탭으로 이관 확정: S8 기술 탭 패널은 판정 기록 진입을 S9 탭 안내로 대체하고 판정 결과를 읽기 전용 블록으로 반영). 원 질의: decider 질의: "그린필드는 S5에서 필요 역량 검증을 했다면, 브라운필드는 S9 실사/검증 단계에서 진행해야 할 듯 한데 맞을까? 만약 맞다면 어떻게 하는게 바람직한지 방안을 제시")
- **후속 결정 (2026-10-20, decider)**: S7 대상 상세의 `필요 역량 점검` 표(S7 대상별 역량 판정, 처리할 것/전체 필터)는 제거 — S6/S7의 기술 평가는 공시·AI 프로파일·웹 근거로 채점하는 기준 항목이고, 격차 해소 검증은 S9 capability-dd만 한다(S7↔S9 비연결). ADR-0171 addendum b.
- **관련**: flow.spec v2.x (S5 applicableTracks [greenfield], S9 [greenfield, brownfield]), ADR-0174 (역량 갭·판정), 2026-10-10-s8-acquisition-price-benchmark

## 1. 문제 — 브라운필드 트랙에서 S3 필요 역량이 검증되지 않는다

- **그린필드**: S5(자체 진출)의 `capability-assessment` 활동이 S3에서 도출한 필요 역량 등록부를 입력으로 받아 역량별 격차·해소 방안을 사람이 판정하고, 그 결과가 투자비(역량 해소 비용)·사업 케이스 라인으로 흘러간다.
- **브라운필드**: S5는 `applicableTracks` 미충족으로 스킵된다. S7 대상 선정의 `역량 적합성`은 **대상별 스크리닝 기준**일 뿐, 기회의 필요 역량 등록부에 대한 격차 판정이 아니다. 그 결과 브라운필드 파이프라인에서는 S3 필요 역량이 이후 어디에서도 사람 검증을 받지 않는다 — "이 인수가 그 격차를 실제로 메우는가?"라는 질문에 대한 기록이 없다.

## 2. 답 — S9가 맞다

- S9의 정의가 곧 근거다: "사실인가? 위험은 무엇인가?" — 대상의 실제 상태에 대한 주장을 검증하는 단계. 필요 역량 격차는 "인수하면 해소된다"는 **주장**이며, 실사에서 대상의 실제 역량을 확인해 검증해야 한다.
- S9의 기존 활동들(technical-dd: 설비·인프라, hr-dd: 조직·인력)이 인접 검증을 이미 수행하지만, **S3 등록부와 연결된 역량별 판정**은 별도로 존재하지 않는다.
- 시점 상 이점: S9 판정 결과를 S10(투자구조)·dd 게이트 판정 근거로 직결할 수 있고, 미해소분 비용을 S8 채택 케이스와 교차검증할 수 있다.

## 3. 설계 — `capability-dd` 활동 (brownfield-dd 절차)

### 3.1 활동 정의 (flow.spec S9 activities 추가)

```yaml
- id: capability-dd
  agent: brownfield-agent        # 또는 commercial-dd-agent — 디스패치 시 확정
  skills: [commercial-due-diligence, org-readiness-assessment]
  procedure: [brownfield-dd]
```

- **입력** (S9 inputs 추가): `S3 필요 역량 등록부 (capability_gap_json — brownfield는 기회에서 읽기)`
- **출력** (S9 outputs 추가): `역량 실사 판정 (역량별: 대상 커버리지·잔여 격차·비용 영향)`

### 3.2 판정 모델 — 역량별 3값 + 근거

S5 판정(AI 초안 → 사람 확정, `capability_gap_json` 부속 구조)을 재사용하되, 브라운필드 질문으로 교체한다:

| 필드 | 그린필드 S5 질문 | 브라운필드 S9 질문 |
|---|---|---|
| 해소 여부 | 자사가 어떻게 해소하는가 (build/partner/hire) | **대상 인수가 이 격차를 해소하는가** |
| 값 | 필요 수준 도달 시기·비용 | `resolved_by_target` (해소/부분 해소/미해소) + 근거(dd_finding 참조) |
| 비용 영향 | 해소 비용 = 투자비 라인 | ~~잔여 격차 해소 비용~~ **제거 (2026-10-19 decider)**: 브라운필드는 인수 자체가 필요 역량 해소 수단이므로 판정에서 비용을 끌내 케이스에 반영하는 구조가 아님 — 판정은 커버리지·근거만 기록 |

- 판정은 **사람 확정** (경계 #2), AI 초안 버튼 가능(대상 공시·DD 발견사항을 근거로 초안 — `s9.capability_dd_draft` 프롬프트 신설 시).
- 저장: `capability_gap_json`의 부속 구조에 브라운필드 판정 블록을 추가하거나(권장 — 등록부와 판정이 함께 이동), 별도 `dd_capability_verdict` 테이블. 마이그레이션 1건.

### 3.3 교차검증 — 제거 (2026-10-19 decider)

- "판정 비용을 채택 케이스에 반영" 경로는 그린필드 사고의 이식 — 브라운필드는 인수 자체가 해소 수단이므로 취소했다. 미해소·부분 해소 건은 **카운트 요약으로만** 의사결정 탭에 노출한다(해소/부분/미해소·미판정 건수; 비용·케이스 반영 없음).

### 3.4 게이트·이후 단계 연결

- dd 게이트(의사결정 탭)에 `역량 실사 판정 요약`(해소 N / 부분 M / 미해소 K / 미판정 P — 카운트만) 노출. 완료 (2026-10-19).
- ~~S10 전달~~ 제거: 비용 개념이 없으므로 전달할 값이 없다 — 미해소 건은 판정 근거 노트로 확인한다.

## 4. 구현 슬라이스 (승인 후)

1. 마이그레이션(판정 저장) + 절차 문서(brownfield-dd에 capability-dd 섹션)
2. flow.spec에 활동·입출력 추가 (S9 inputs/outputs, activities)
3. S9 화면: 역량 실사 판정 표 (S3 등록부 로드, 사람 판정 PUT, AI 초안 버튼)
4. 교차검증 경고 + 게이트 요약 노출
5. 테스트: 판정 저장/조회, 교차검증 경고, 게이트 요약

## 5. 열린 질문

- 판정 주체 에이전트: brownfield-agent vs commercial-dd-agent (디스패치 계층에서 확정 가능)
- 판정 저장 위치: capability_gap_json 부속(권장) vs 독립 테이블 — 등록부 수명과 판정 수명의 일치 여부로 결정
- 대상별(선정 대상 1개 + 선택 비교 대상) 판정을 모두 저장할지 — ADR-0157 선택적 대상별 DD 선례 따름
