# 위키 handbook 표준 재작성 설계 (2026-10-23)

한국어 사용자 안내서 위키(`docs/wiki/ko/`, 39개 md 파일)를 `.agents/skills/handbook`의 저작 기준으로 다시 쓰는 재구성 설계다. 이 문서는 기존 위키 설계 [2026-10-13-user-manual-wiki-design.md](2026-10-13-user-manual-wiki-design.md)를 **수정(amend)**한다. §7.2 페이지 틀과 §10 집필·검증 계획을 대체·보강하며, §10.2의 라벨 검증 의무와 §8 스크린샷 기준은 그대로 유효하다. 이번 설계는 **구조 정비 + 문체 통일**이지 사실 재작성이 아니다. 2026-10-23에 병합된 화면 갱신 묶음에서 검증한 화면 라벨·경로·사실은 전부 살려 둔다.

## 1. 배경·의도

### 1.1 결정 문구 (decider)

> "wiki 문서가 제대로 만들어지지 않은 듯, handbook 스킬 기준으로 본 프로젝트 wiki 구조를 유지하며 재작성"

해석: (a) 여정 지도·쪽 나무·트랙 길로 정의된 **위키 구조는 유지**한다. (b) 쪽의 **저작 품위를 handbook 기준으로 맞춘다**(개념-먼저 서술, 한 단계=한 동작, 문체·표기·내비 규범). (c) 화면 라벨 등 검증된 **사실은 재검증 없이 보존**한다.

## 2. 재작성 원칙 (구조는 유지, 품위는 교체)

바꾸지 않는 것: 쪽 나무(§7.1), 파일명·슬러그, `_Sidebar.md` 그룹 구조, 이미지 자산, frontmatter 필드 체계, H1 제목, 데모 안내 문구 체계.

바꾸는 것: 쪽 골격(절 집합과 순서), 문장 종결, 줄표·날짜·용어 표기, 내비(이전/다음 사슬), 개념 블록 신설.

### 2.1 쪽 유형 → 틀 깊이 매핑

| 틀 | 쪽 (doc_type frontmatter) | 개념 블록 `왜 이 단계인가` | 필수 절 | 비고 |
|---|---|---|---|---|

| 연습 (practice) | 01-시작하기, 90, 91-따라하기-점검표 (3쪽) | 면제 | 목적 머리 · 데모 안내 콜아웃 · 체크리스트 절 · 마무리 · 내비 행 | 90의 마무리는 91로, 91의 마무리는 실무 적용 행동 목록으로 (§15-1 환산) |

frontmatter `doc_type` 값은 이번 묶음에서 바꾸지 않는다(§3.6 불변 1).

### 2.2 전형(how-to) 쪽 골격 — 재작성 계약

모든 전형 쪽이 아래 순서와 어휘를 따른다. 괄호 주석은 지침이고 실제 쪽에는 넣지 않는다.

```markdown
---
doc_type: how-to
stage: S7                          # 단계 쪽만. 값은 기존 그대로
tracks: [greenfield, brownfield]   # 기존 그대로
personas: [P2, P1]                 # 기존 그대로
route: /deals/{id}/s7              # 기존 그대로
verified_on: YYYY-MM-DD            # 기존 값 유지 — 이 묶음은 사실을 바꾸지 않는다
verified_build: <기존 값>           # 있는 쪽만, 기존 값 유지
lang: ko
lang_reason: source-material
---
# (H1 제목 — 기존 문장 그대로 유지)

**목적:** 한 문장. 이 화면이 무엇을 기록하고 무엇을 여는지.
**누가/언제:** 역할과 진입 시점(바로 앞 게이트 이름).
**사전 조건:** ① 바로 직전 단계·게이트 ② 필요 권한(역할) ③ 준비물(데모 안건 이름 등). 빠짐없이 적는다.

> [!NOTE]
> **트랙:** 트랙마다 달라지는 점 요약과 양쪽 길 링크. 공통 단계이고 차이가 없으면 이 상자는 생략.

> [!NOTE]
> 이 쪽의 화면 그림은 **데모 자료**입니다. 안건 이름, 규모, 점수는 내 자료와 다릅니다.   ← 기존 공통 문구 유지

## 왜 이 단계인가

(3~5문장. ① 이 단계가 여정에서 답하는 질문 ② 바로 앞 단계와의 인과 ③ 사람·AI 경계나
불변 기록 같은 제도적 이유 ④ 비유 1개 ⑤ 다음 절로 연결. 새 주장·수치·순서를 만들지
않고 flow.spec.yaml 단계 목적과 이미 검증된 사실에서만 쓴다. 새 용어 첫 출현은
`한국어(English)` 표기.)

![화면 캡처](images/기존-파일.png)
*캡션: 어떤 화면인지, 어느 데모인지 — 식별 정보는 유지하고 문장만 고친다.*

## 단계

1. (읽기) `화면 라벨`이 어떻게 보이는지 읽는다.
2. (쓰기) `입력 칸`에 값을 넣는다.
3. (사람만) **결정**을 누른다.
(한 단계 = 한 동작. 저장·확인 누르기는 단계 하나에 최대 하나. 접두 표기
(읽기)/(쓰기)/(선택)/(사람만)은 기존 관습을 그대로 쓴다.)

## 결과 확인

- 화면에 남는 변화와 어디서 보이는지. 불변 기록의 성격이면 그 사실을 명시.

## 자주 하는 실수

- 오해 한 줄 + 바른 읽기 한 줄. (명사 종결 "~것." 유지)

## 알려진 불일치        ← 이미 있는 17쪽만. 결함 기록 번호(D-xx) 연결 유지

## 스스로 확인하기

데모 안건에서 읽기 전용으로 확인할 과제 1개. 어떤 버튼도 누르지 않는다는 문장 유지.

## 핵심 요약

- 3~5개 항목. 이 쪽의 동작·경계·다음 길을 한 줄씩.

이전: [NN-이전-쪽](NN-....md) | 다음: [NN-다음-쪽](NN-....md)
```

절 순서 고정: 왜 이 단계인가 → 단계 → 결과 확인 → 자주 하는 실수 → 알려진 불일치(있으면) → 스스로 확인하기 → 핵심 요약 → 내비 행. H2 어휘는 위 표기 그대로(쪽마다 변형 금지). 마지막 줄의 내비 행은 `## 다음 단계` 절을 대체한다 — 기계적 사슬은 내비 행이 담당하고, 분기 안내 같은 서술형 안내는 `왜 이 단계인가`와 트랙 콜아웃이 이미 담당한다.

### 2.3 나머지 유형 골격 요약

- 서사(Home/10/11): 목적 머리 + 데모 콜아웃 → 여정 개요(펜스 다이어그램 또는 표) → 해설 절들(기존 절명 유지 가능) → `## 핵심 요약` → 내비 행. Home은 내비 행 `다음:`만 둔다(§3.4).
- 연습(01/90/91): 목적 머리 + 데모·읽기 전용 콜아웃 → 번호 붙은 체크리스트 절 → `## 마무리` → 내비 행. 체크리스트 항목의 "~했다" 종결 유지.
- 참조(02/03/04/12/60/70/80/81/82): 목적 머리 + 데모 콜아웃 → 본문 절(표 중심) → 내비 행. 개념 블록·핵심 요약 강제 없음. 82-변경-이력은 내비 행만 붙이고 표 구조는 그대로.

### 2.4 이전/다음 사슬 정의

`_Sidebar.md`가 읽기 순서의 기준(SSOT)이다. 내비 행은 아래 규칙으로 사이드바에서 결정적으로 유도되며, 이 문서의 사슬표가 그 유도 결과다.

- R1 (직선 규칙): 그룹은 사이드바 순서대로 잇고, 그룹 안 항목은 나열 순서대로 잇는다. Home이 사슬의 처음이다.
- R2 (갈림길 규칙): 23-공통-S4-진출방식-결정의 `다음`은 두 길의 입구를 모두 나열한다 — `[10-그린필드-여정] · [11-브라운필드-여정]`. 각 길 입구(10, 11)의 `이전`은 23이다.
- R3 (합류 규칙): 각 길의 마지막 쪽(45, 56)의 `다음`은 합류 지점 30-공통-S8-사업성-분석 하나다. 30의 `이전`은 45와 56을 모두 나열한다.
- R4 (끝 규칙): 마지막 쪽(91)은 `다음`이 없다. `이전: [90] | 처음: [Home](Home.md)` 내비 행과 함께 `## 마무리`에 실무 적용 행동 목록을 둔다(§15-1 환산).
- R5 (상호성 규칙): A의 `다음` 목록에 B가 있으면, B의 `이전` 목록에 A가 있다. 그 역도 성립한다. 23의 두 번째 분기 목표(11)는 R2가 `이전`을 23으로 정하므로 예외가 없다.

### 2.5 문장 규범

**평서체 (S1, §12-1).** 본문·캡션·콜아웃의 종결을 평서체(`~한다/~이다/~없다`)로 통일한다. 현행 위키는 `~합니다`체(합쇼체)라 전 쪽 종결 치환이 필요하다. 기계적 치환이지만 사실은 하나도 바뀌지 않는다. 단계 서술은 "`버튼`을 누른다", 자주 하는 실수 항목은 명사 종결("~것.")을 유지, 체크리스트 항목("~했다")은 이미 평서라 유지. backtick 화면 라벨은 종결 치환 대상이 아니다.

**긴 줄표 (E1~E3, §12-4).**
- E1: 본문·캡션의 — 는 문장 분리(`.`)나 콜론(`:`)으로 바꾼다. 캡션도 대상이다.
- E2: 머리 라벨 구분자를 콜론으로 통일한다: `**목적:**`, `**누가/언제:**`, `**사전 조건:**`, 콜아웃 `**트랙:**`, `**Green Field에서만:**`. 현행 `**목적** —` 템플릿이 줄표를 낳았으므로 틀부터 고친다.
- E3(보존): backtick 안의 — 는 화면 표기라 그대로 둔다. 예: `Greenfield — 자체 역량으로 진출`, `설립 실행 — 5단계`, `동기화 전 — 회사 화면에서 동기화하세요`, 표의 빈 값 `—`. 판정법: backtick 구간을 벗긴 뒤 본문의 — 가 0이어야 한다.

**날짜 각인 (D1~D4, §5a).**
- D1: 본문(frontmatter 제외)에 달력 날짜를 쓰지 않는다. 예외 3종: backtick 안 화면 값(`기준 시장규모 (2026)`, 예시 입력 `2026-Q4`), `82-변경-이력.md`의 표, `_Footer.md`의 검증 기준일(기존 설계 §7.1이 선언한 "마지막 검증 시점"이며 §21-6도 이 기준일을 허용한다 — 신선함 판단 정보지 새로움 선전이 아니다).
- D2: `60-프로젝트-화면-안내.md`의 날짜 붙은 소제목 2개에서 날짜를 떼고 본문 흐름에 접어 넣는다.
- D3: 변화 서사 어휘("~되었습니다", "예전에는", "이제", "없어지고 …충분해졌습니다")를 현재 상태 서술로 바꾼다(60번의 프로젝트 목록·에이전트 실행 이력·외부 안전 공유 절, 45번 1곳). 바뀐 이력은 82에만 남는다.
- D4: frontmatter `verified_on`/`verified_build`은 유지한다. 이 묶음이 라벨을 바꾸지 않는 한 재검증·갱신하지 않는다.

**용어 표기 (T1~T3, §12-2).**
- T1: 새로 쓰는 문장에서 기술 용어 첫 출현은 `한국어(English)`(예: 진출방식(트랙·라우트), 인수합병(M&A)), 같은 파일의 이후 출현은 단독. 파일(쪽)별 기준.
- T2: H2/H1 제목에는 괄호 용어 표기를 새로 넣지 않는다. 화면 라벨이 제목에 그대로 들어가는 경우(`WACC 읽기`, `M&A 필수 검증 여섯 가지`)는 라벨이라 그대로 둔다. 위키는 기본 한국어판이라 §12-2의 한국어 헤딩 예외가 적용된다.
- T3: backtick 화면 라벨은 이 규범의 대상이 아니다(사실이므로 불변).

**상호 참조 (X1, §12-3 환산).** 쪽 참조는 `[슬러그](슬러그.md)` 형식만 쓴다("다음 장에서" 같은 맨말 참조 금지). 쪽 안 절 참조는 `[절 제목](#제목-슬러그)` 앵커나 제목을 그대로 인용한 따옴표 참조("「단계」 절")를 쓴다. 제목 슬러그는 `wikiHeadingSlug` 규칙(소문자화, 구두점 제거, `&`→하이픈, 공백→하이픈, 한글 보존, 중복 시 `-1` 접미)을 따른다.

**사전 조건 완전성 (P1, §7).** 전형·연습 쪽의 사전 조건은 ① 직전 단계·게이트 ② 권한(역할) ③ 준비물(데모 안건 이름 등) 세 요소를 빠뜨리지 않는다. "당연한 것"으로 치고 생략하지 않는다. 부족한 기존 쪽은 이미 검증된 사실 범위에서 채운다.

**한 단계 = 한 동작 (A1~A3, §2).**
- A1: 저장·확인 등 누르기 동작은 단계 하나에 최대 하나. 서로 독립된 누르기가 둘 있으면 단계를 나눈다.
- A2: (읽기)/(쓰기)/(선택)/(사람만) 접두 표기를 유지하고 전 쪽에서 같은 의미로 쓴다.
- A3: 한 화면 영역을 통째로 읽기는 한 동작으로 친다 — 과잉 분해하지 않는다.

**절별 시각 요소 (V1, §10-1 환산).** 마크다운의 시각 요소는 {이미지(`images/*.png`), 표, 펜스 다이어그램, `> [!NOTE|TIP|WARNING]` 콜아웃, 체크리스트} 다섯 종. 전형·서사·연습 쪽의 해설 성격 H2 절(왜 이 단계인가, 단계, 결과 확인, 자주 하는 실수, 두 트랙 비교 등)에는 최소 1개를 둔다. 스스로 확인하기·핵심 요약·내비 행은 면제. 참조 쪽은 쪽 단위로 표나 이미지 1개 이상(참조 문서 면제 규정의 환산).

**V1 면제·후속 (AI 2차 검토 결정, 2026-10-23).** 고정 골격(§2.2)이 자체 정형을 선언한 절차 절(`단계` 번호 단계, `결과 확인`, `자주 하는 실수`, `스스로 확인하기`)은 V1의 절별 시각 요소 의무에서 면제한다. 골격 우선이다: §2.2가 이 절들의 정형을 목록·표(쪽이 고른 형태)로 이미 정의했고, 매 절에 그림을 억지로 넣으면 명료함이 아니라 잡음이 된다. V1의 시각 의무는 해설·주제 절(예: 왜 이 단계인가, 리스크 히트맵·백테스트·마일스톤·합작 조건 같은 이름 붙은 주제 절)에 적용되며, 표·펜스·콜아웃·이미지를 이미 하나 이상 지닌 절은 오늘 기준으로 충족한 것이다. 검토에서 적발된 본문만 남은 주제 절(31 리스크 히트맵, 32 부지·시설과 인허가·인증, 34 백테스트·마일스톤·실행 기준선 대비 차이와 학습 코퍼스, 54 합작 조건 기록하기, Home 처음이라면)은 시각 보강 후속 과제로 기록한다(기존 캡처 재사용 또는 사실에서 유도한 표). 이는 이 재작성 묶음의 범위 밖이다. 다섯 곳의 시각 보강 후속은 2026-10-23에 완료했고, 기록은 `82-변경-이력`의 새 행에 남았다.

### SVG 채택과 접두어 철회 (2026-10-24 결정)

결정자가 재구축된 위키를 앱에서 검토하고 내린 세 가지 방향이다.

**SVG 채택.** 설명에 도움이 되는 다이어그램은 인라인 `<svg>`로 쓴다. handbook AUTHORING_GUIDELINES §10-2를 마크다운에 맞게 환산한 규칙을 따른다: `viewBox` + `width="100%"`(반응형), 색은 CSS 변수만(`var(--fg)`, `var(--border)`, `var(--primary)`, `var(--muted-fg)` — 다크 모드 대응), 라벨은 한국어, 접근성을 위해 `role="img"` + `<title>`. 마크다운은 펜스가 없어도 렌더러가 원본 HTML을 통과시키므로(검증됨) SVG의 `<` 문자가 문제되지 않는다. 대체되는 ASCII 펜스는 사본으로 남기지 않고 지운다.

**접두어 철회.** 재작성에서 쓴 단계 접두어 `(쓰기)`/`(선택)`/`(사람만)`/`(읽기)`는 독자를 혼란스럽게 하므로 철회한다. §2.2 틀의 접두 표기 지침과 §2.5 A2는 이 결정으로 대체된다. 사람 전용 강조는 앱 화면 문구가 이미 표시하는 자리(`결정 기록 (사람)` 등)와 각 쪽의 트랙·NOTE 콜아웃이 담당한다. 선택 단계는 선택성이 의미 있을 때 문장을 "필요하면"으로 시작하는 평범한 단계가 된다. backtick 화면 라벨 안의 `(선택)`(`라우트 (선택)` 등)은 화면 사실이라 이 철회의 대상이 아니다.

**가독성 CSS (별도 디스패치).** 본문 측정폭 제한과 타이포 리듬은 뷰어 CSS에서 적용한다.

### 2.6 보존 불변 목록 (DO-NOT-BREAK)

재작성 중 어떤 편집도 아래를 깨지 않는다. 검증 계획(§4)이 각 항목의 위반을 잡는다.

1. **frontmatter 필드**: 필드 이름과 값(doc_type, stage, tracks, personas, route, verified_on, verified_build, lang, lang_reason)을 유지. 절차상 새 필드를 추가하지 않는다.
2. **검증된 사실**: backtick 화면 라벨·값, 경로, 게이트 이름, 권한 서술, 사람 전용 경계 문구("결정은 사람이 기록합니다" 계열), 데모 안건 이름. 이 묶음에서 라벨을 하나도 바꾸지 않는다 — 바꿀 필요가 생기면 이 묶음에서 빼고 §10.2 라벨 검증 절차를 밟는 별도 변경으로 처리한다.
3. **H1 제목**: 생성기가 `^#\s+`로 페이지 제목을 뽑으므로 H1 문장을 유지한다. 제목 변경은 별도 결정 사안이다.
4. **파일명·슬러그**: 쪽 파일명을 바꾸지 않는다(링크·사이드바·투영 키가 전부 이에 묶인다).
5. **이미지 자산**: 기존 `images/*.png` 83장과 `capture-manifest.json`을 그대로 재사용한다. 이 묶음에서 새 캡처를 찍지 않고 이미지 참조를 지우지 않는다. 캡션은 문장만 고칠 수 있고 식별 정보(어느 화면, 어느 데모)는 유지한다.
6. **82-변경-이력**: 기존 행은 건드리지 않는다(append-only). 이 재작성 묶음을 마칠 때 새 행 하나를 덧붙인다.
7. **앵커 계약**: 제목 문장을 바꾸면 슬러그가 바뀌므로, 같은 편집에서 그 제목을 가리키는 모든 앵커(`[...](#슬러그)`, `[...](X.md#슬러그)`)를 함께 고친다. 현존 앵커 2개 — `53-브라운필드-S9-실사.md`의 `#m-a-필수-검증-여섯-가지`와 `54-브라운필드-S10-거래-구조.md`의 `#합작-조건-기록하기` — 을 특히 유의한다. `sync-wiki-projection.ts`의 내장 앵커 검증이 어긋나면 빌드가 실패한다. 고치는 쪽은 렌더러가 아니라 원본 링크다.
8. **링크 문법**: 쪽 안 원본은 렌더러가 지원하는 네 형태만 쓴다 — 상대 `X.md`(`.md` 생략형도 가능하나 통일을 위해 `.md`를 붙인다), `images/…`, 쪽 안 `#앵커`, 폴더 밖 `../../manuals/*.md`(뷰어가 `/library?doc=`로 재작성). `/wiki/...` 같은 앱 경로를 원본에 링크로 쓰지 않는다(재작성되지 않고 깨진 링크로 보인다).
9. **데모 안내 콜아웃**: "화면 그림은 데모 자료" 계열 공통 문구를 전 쪽에 유지한다(문장은 평서체로 맞춘다).

## 3. 검증 계획

실행 순서: 쪽 묶음 편집 → ① → ② → ③ → ④. 전부 통과해야 묶음을 닫는다.

1. **링크 검사**: `bun scripts/validate-docs-links.ts --dir=docs/wiki/ko` — 상대 링크와 앵커 조각의 1차 검증.
2. **생성기 검증**: `bun scripts/co-newbiz/sync-wiki-projection.ts --check` — 내장 검증 다섯 종(폴더 안 링크 ⊆ 페이지 집합, 이미지 ⊆ 허용목록, 쪽 안·교차 앵커 ⊆ 헤딩 슬러그, 사이드바 파싱, H1 존재)과 투영 최신성. 실패 시 원본 `docs/wiki/ko/`을 고치고 다시 돌린다.
3. **내비 검사기**: `scripts/co-newbiz/check-wiki-nav.ts` (별도 디스패치로 구현). handbook `validate-nav`의 마크다운 환산으로, 다음을 검사한다: (a) 전 쪽 내비 행 존재, (b) R5 상호성(다중 목표 포함, §2.4 사슬표와의 일치), (c) 내비 링크 문구 = 대상 슬러그, (d) 끝 쪽(91)의 마무리 행동 절 존재, (e) 부가 게이트 — backtick을 벗긴 본문의 — 밀도 0(E1~E3), 본문 달력 날짜 0(예외 3종 제외, D1), 유형별 필수 H2 절 존재(§2.1~2.2).
4. **3쪽 수동 정독 (§19)**: `23-공통-S4`(갈림길 전형), `60-프로젝트-화면-안내`(참조), `91-따라하기-점검표-브라운필드`(연습·사슬 끝)를 처음부터 끝까지 읽어 오탈자·비문·번호 불일치·인과 뒤집힘을 잡는다. 3단계 검토 적용 — docs-writer 초안 → 다른 영역 에이전트 교차 검토(process-governance-manager: 절차 중복 서술이 없는지, 게이트·사람 전용 서술이 정확한지) → 사람 최종.

- GitHub 위키 미러링 관련 변경(미러 스크립트·배포는 이 묶음과 무관).
- 영어 번역 및 다중 언어 변주.
- 사실·라벨 재검증(라벨 검증 의무는 기존 설계 §10.2에 그대로 살아 있고, 이 묶음은 라벨을 바꾸지 않으므로 발동하지 않는다).
- 파일명·H1 제목·frontmatter 필드 체계 변경.
- `82-변경-이력.md` 기존 행 수정(새 행 추가만 허용).

## 5. handbook 참조 중 제외한 항목 (HTML 전용 규격)

| 항목 | 제외 이유 (한 줄) |
|---|---|
| §2 Copy 버튼·copy-code.js | HTML 위젯 규격이고 위키 원본은 마크다운이라 버튼 문법 자체가 없다. |
| §3 AGENTS.md 선행 도구 중립 명세 | 다중 에이전트 도구 교육용 규범으로, 앱 화면 안내 콘텐츠와 무관하다. |
| §5 조직 규모 일반화 | "핸드북에 관한 핸드북" 성격의 규범이고 위키는 시스템 인스턴스 하나를 설명한다. |
| §6 시간 제약·배분표 | 위키에 배분표가 없고 Home의 "15분" 안내는 제약이 아닌 참고 정보라 유지한다. |
| §8 HTML 출력·좌측 내비·사이트 검색 | 위키는 .md 원본이 SSOT이고 렌더는 GitHub/인앱 뷰어가 담당한다(기존 설계 §1, §7.4). |
| §10-2~10-4 SVG·CSS 컴포넌트 규격 | HTML/CSS 자산 규격이라 마크다운 대응물이 없고, 그 자리는 표·펜스·콜아웃이 대신한다(V1). |
| §11 계열(flex min-width, a 중첩, .table-schedule) | 렌더 산출물의 CSS/HTML 구조 검사라 .md 원본에 적용 불가다. |
| §12-2 헤딩 영어 단독 규칙 | §12-2의 한국어 기본판 예외가 적용되어 한국어 헤딩을 유지한다(제외가 아니라 예외 적용). |
| §14 강의 개관 9항목 | 과정(course) 자료 규범이고 오리엔테이션은 Home과 04-역할별-시작-페이지가 이미 담당한다. |
| §17 동영상 참조 5단계 검증 | 화면 안내에 공식 교육 영상 체계가 없다. |
| §18 A/B 플랫폼 분리 | 도구 간 구현 차이 규범이며, 트랙 갈림길은 이미 콘텐츠 구조(트랙 콜아웃·길 쪽)로 해결돼 있다. |
| §20 강사 가이드 6절 | 강사·수강 체계가 없다. |
| §21-5 meta description, §21-6 푸터 3줄 라이선스, §22 다크모드 CSS 변수 | HTML 페이지 규격이고 위키 푸터는 기존 설계 §7.1 선언(면책 + 검증 기준일)을 따른다. |
| §23 다중 언어 파일 변주 | `docs/wiki/ko`는 단일 로케일 구역이고 번역은 범위 밖이다. |

참고로 §4a(사설 저장소 참조 금지)는 제외하지 않는다 — 위키 링크가 전부 공개 저장소 내부 상대경로라 위반 소지가 없을 뿐, 원칙은 그대로 유효하고 검증 계획 ①의 링크 검사가 사실상의 점검이다.
