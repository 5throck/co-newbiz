# 사용자 안내서 위키 인앱 뷰어 — 설계

- **Spec ID**: `2026-10-23-wiki-in-app-viewer-design`
- **상태**: implemented — D1~D8대로 구현됐다(생성기 `scripts/co-newbiz/sync-wiki-projection.ts` → `app/web-next/lib/wiki.generated.ts`, `/api/wiki`·`/api/wiki/[slug]`·`/api/wiki/images/[file]`, `/wiki`·`/wiki/[slug]` 화면, 내비 등록·드리프트·뷰어 단위 시험). 본문의 "승인 단계" 서술은 승인 시점의 기록으로 남긴다.
- **관련 문서**: `docs/designs/2026-10-13-user-manual-wiki-design.md`(위키 자체 설계), ADR-0105(내비게이션 SSOT), ADR-0108(문서 허브 단일 표면), `docs/context.md`(언어 정책)

## 1. 배경과 문제

`docs/wiki/ko/`는 사용자 여정 순서로 편성된 한국어 사용자 안내서 위키다. 본문 페이지 36개 + `Home.md` + `_Sidebar.md` + `_Footer.md`, 그리고 `images/` 밑에 캡처 PNG 83장(약 4.9MB). GitHub 위키 1:1 미러링을 전제로 만들어져 있다(2026-10-13 설계 §7.4).

사용자 요청: **"위키를 사이드바에서 볼 수 있도록 해주면 좋을 듯 해"** — 지금은 앱 안에서 이 안내서를 볼 길이 없다. 사용자가 안내서를 보려면 저장소(또는 GitHub)를 직접 열어야 한다.

목표는 웹 앱의 표준 인증 화면 안에서 `/wiki`로 위키를 열람하게 하는 것이다. 제약은 하나다. **`docs/wiki/ko/`는 그대로 SSOT로 남는다.** 뷰어는 읽기 전용이고, 원본 마크다운·이미지를 복제·변형하지 않는다(GitHub 미러링과 레포 열람은 계속 같은 원본을 본다).

## 2. 읽은 근거

- `app/web-next/lib/navigation.ts` — 내비 SSOT(ADR-0105). "분석·참조" 구간 현재 순서: `/benchmarks`, `/library`, `/glossary`, `/strategy`. `NON_MENU_ROUTES`에 없는 `page.tsx`는 `tests/unit/navigation.test.ts`의 패리티 검사에서 고아(orphan)로 탈락한다.
- `tests/unit/navigation.test.ts` — 메뉴↔페이지 패리티, 빈 href 금지, 중복 금지. 동적 세그먼트(`[`)가 들어간 NON_MENU_ROUTES 항목은 존재 검사를 건너뛴다(69–73행).
- `app/web-next/lib/library.ts` + `app/web-next/lib/library.generated.ts` + `scripts/co-newbiz/sync-library-projection.ts` + `tests/unit/library-projection-sync.test.ts` — 저장소 문서의 기존 패턴: **체크인된 생성 정적 투영**. 넓은 fs 순회를 서버 경로에서 하지 않게 하는 것이 목적. 생성기는 `--check`로 스테일 시 exit 1. **dev-sync.ts에는 이 생성기에 대한 참조가 전혀 없다** — 갱신은 수동이고, 강제는 단위 시험 스위트가 도는 드리프트 가드 테스트다(CHANGELOG 2026-10-01: "CI `library-projection-sync` failure").
- `app/web-next/app/library/page.tsx` + `app/api/library/route.ts` + `app/api/library/[docId]/route.ts` — 목록/본문을 API로 나눠 서브고, `marked`(^18.1.1, `app/web-next/package.json`)로 클라이언트에서 렌더한다. `[docId]` 경로의 보안 포즈: "Ids are generated by lib/library.ts … never raw paths, so there is no client-controlled path component reaching the filesystem."
- `app/web-next/app/api/admin/adr/route.ts` — 런타임에 레포 파일을 읽는 기존 선례: cwd에서 위로 걸어 올라가 `docs/adr` 마커를 찾는다("same discipline as scripts/co-newbiz/proc-resolve.ts").
- `docker/Dockerfile` — 프로덕션(7749, Cloudflare 터널)은 **런타임 스테이지가 `docs/`를 이미지에 복사**한다(`COPY --from=build /repo/docs ./docs`). `CMD`는 `bun --bun next start` — 레포 트리 위에서 도는 in-place 구동이고 standalone 번들(None.output `standalone`)이 아니므로 NFT 추적 문제가 없다.
- `app/web-next/lib/auth.ts` `authenticate()` — 세션 쿠키(`co_newbiz_session`) **또는** Bearer 토큰을 받는다. 같은 오리진 `<img src>` 요청에는 브라우저가 세션 쿠키를 자동으로 실어 보내므로, 인증이 필요한 이미지 경로도 `<img>`로 렌더할 수 있다.
- `docs/wiki/ko/` 실측 — 마크다운 합계 348KB. frontmatter 필드: `doc_type, stage, tracks, personas, route, verified_on, verified_build, lang, lang_reason`. 링크는 폴더 안 상대 `*.md`(`[x](31-공통-S9-실사.md)`), 이미지는 `images/*.png`. **`Home.md`·`04-역할별-시작-페이지.md`·`70-관리자-화면-안내.md`의 3개 문서는 `../../manuals/*.md`(위키 폴더 밖) 링크를 가진다.** 34개 문서가 GitHub alert 문법(`> [!NOTE]`/`> [!WARNING]`)을 쓰고, `53`·`54`번 페이지에 페이지 내 앵커 링크(`](#m-a-필수-검증-여섯-가지)` 등)가 있다.
- `marked` v18 — 기본으로 헤딩 id를 붙이지 않고(headerIds는 v5에서 제거), GitHub alert 문법도 지원하지 않는다. 둘 다 렌더러 층에서 처리해야 한다.

## 3. 결정

### D1. 전용 경로 `/wiki`(인덱스)와 `/wiki/[slug]` — /library 카테고리로 넣지 않는다

문서 허브(/library)는 고정된 문서 단위 레지스트리다(카테고리 탭 × id 기반 문서, `chk-*`/`man-*` 식별자). 위키는 36페이지짜리 여정 순서 매뉴얼로 자체 정보구조(`_Sidebar.md`의 여정 그룹)를 가진다. 위키 페이지를 /library의 카테고리로 흡수하면 (a) 허브의 카테고리 탭 의미가 무너지고 (b) 여정 순서·그룹 내비가 사라진다.

- `/wiki` — 인덱스. `Home` 본문 + 전체 페이지 목록(여정 그룹).
- `/wiki/[slug]` — 본문 열람. slug = 파일명에서 `.md`를 뺀 것(`Home`은 인덱스로 특수 취급).
- 내비 패리티: `/wiki`는 메뉴 등록(D6), `/wiki/[slug]`는 `NON_MENU_ROUTES` 등재(동적 세그먼트라 존재 검사는 건너뛰지만, 고아 검사를 통과하려면 명시적 탈메뉴 등록이 필요하다 — navigation.ts 70–73행 주석의 원칙).

**기각안**: /library에 "사용자 안내서" 카테고리 추가 — 위의 (a)(b) 때문에 기각. 기존 wiki 디렉터리를 앱 폴더로 옮기는 것 — GitHub 미러링 전제(2026-10-13 설계)를 깨므로 기각.

### D2. 생성 정적 투영 — `scripts/co-newbiz/sync-wiki-projection.ts` → `app/web-next/lib/wiki.generated.ts`

라이브러리 패턴(§2 네 번째 근거)을 그대로 따른다. 페이지 39개 마크다운 합계 348KB로 `library.generated.ts`(972KB)보다 작아, **본문 통째 포함**이 부담 없다. 서버 경로가 `next build` 때 넓은 fs 순회를 하지 않는다는 라이브러리의 원래 동기가 그대로 적용된다.

라이브러리 생성기와의 차이 한 가지: 라이브러리 생성기는 기존 항목만 갱신하고 추가/삭제는 손으로 한다(v1 주석 — id·카테고리가 사람이 고르는 메타데이터이기 때문). 위키는 페이지 집합 자체가 파일 집합이고 제목·frontmatter·순서가 전부 파생 값이므로, **위키 생성기는 전면 재생성**으로 만든다. 페이지 추가/삭제가 투영에 기계적으로 반영된다.

**`/sync` 연결 — 권고안의 전제를 실측에 맞게 바로잡는다.** "「/sync」가 라이브러리 투영 단계와 나란히 돌린다"는 표현은 사실과 다르다. dev-sync.ts에는 `sync-library-projection.ts`에 대한 참조가 없고, 라이브러리의 실제 강제 장치는 단위 시험 스위트가 도는 **드리프트 가드 테스트**(`tests/unit/library-projection-sync.test.ts`)다. 위키도 같은 자리를 쓴다: 수동 갱신 명령(`bun scripts/co-newbiz/sync-wiki-projection.ts`, `--check` 지원) + 신설 드리프트 테스트. /sync는 단위 시험을 돌므로 스테일 투영은 /sync에서 잡힌다. dev-sync에 생성기 단계를 새로 추가하는 것은 이 설계 범위 밖이다(§8).

**기각안**: 런타임 fs 읽기(페이지별로 `docs/wiki/ko`를 읽는 경로 핸들러) — 라이브러리가 NFT 추적 회피를 위해 버린 길이고, 본문이 작아 끼워 넣기가 공짜인 지금 다시 택할 이유가 없다. 빌드 때 pages를 개별 route로 생성(36개 page.tsx 생성) — 생성물이 앱 트리를 오염시키고 내비 패리티 검사 대상이 36개로 늘어난다. 기각.

### D3. 슬러그 허용목록 — 클라이언트가 통제하는 경로 구성요소는 fs에 닿지 않는다

`/api/wiki/[slug]`는 `wiki.generated.ts`의 키 집합에서만 해석한다. 키에 없으면 404. `/api/library/[docId]`와 동일한 포즈("never raw paths"). 이미지 파일명도 같은 원리다(D4).

### D4. 이미지는 경로 핸들러로 fs 서빙 — `public/` 복사 없음

`/api/wiki/images/[file]` 경로 핸들러가 `docs/wiki/ko/images/`의 PNG를 `fs.readFile`로 읽어 `Content-Type: image/png`으로 내린다. 허용목록은 생성기가 `wiki.generated.ts`에 박아 넣은 **파일명 목록**(83개)이며, 목록에 없는 이름은 `path.basename` 정규화 후 무조건 404다(traversal 시도는 허용목록 자체가 차단한다).

fs 서빙이 프로덕션에서 성립하는 근거(실측): 런타임 Docker 이미지가 `docs/`를 통째로 싣고(Dockerfile 런타임 스테이지 `COPY --from=build /repo/docs ./docs`), `next start`는 레포 트리 위에서 돈다. 런타임 레포 파일 읽기의 기존 선례도 있다(`app/api/admin/adr/route.ts`의 walk-up 마커 탐색 — 이미지 경로도 같은 규율로 `docs/wiki/ko/images` 마커를 찾아 올라간다).

**캐시는 immutable로 하지 않는다(권고안 조정).** `immutable`(1년) 캐시는 파일명이 내용 불변일 때만 안전한데, 캡처 파일명은 재촬영 때 **같은 이름으로 덮어써진다**(`capture-manifest.json`의 `common-01-login.png` 같은 id가 고정). immutable을 붙이면 재촬영한 캡처가 사용자 브라우저에 1년간 안 바뀐다. 대신 **ETag(크기+mtime) 재검증 + 짧은 max-age**(예: `no-cache` + ETag, 또는 `max-age=300`)로 둔다.

**기각안**: `app/web-next/public/wiki/images/` 복사 — 4.9MB 이중 보관 + 두 번째 SSOT(복사 타이밍이 어긋나면 앱과 원본이 다른 그림을 보여준다). 기각. base64를 generated.ts에 박아 넣기 — 클라이언트가 import하는 모듈이 6.5MB(+33%)로 부풀어 /wiki 방문자 번들뿐 아니라 generated 모듈을 함께 번들링하는 모든 서버 경로에 영향. 기각.

### D5. 렌더 시 링크 재작성 — 원본 마크다운은 건드리지 않는다

페이지 컴포넌트가 렌더 직전에 순수 함수로 재작성한다(`lib/wiki.ts` — 단위 테스트 대상). 원본은 절대 변형하지 않는다(레포 열람·GitHub 미러가 같은 원본을 본다). 규칙:

1. **폴더 안 `.md` 링크** `[텍스트](31-공통-S9-실사.md)` → `/wiki/31-공통-S9-실사`. 대상이 투영 페이지 집합에 없는 링크는 재작성하지 않고 그대로 둔다(렌더 후 깨진 링크로 보이는 것이 무음 재작성보다 낫다).
2. **`Home.md`** → `/wiki`.
3. **이미지** `images/x.png` → `/api/wiki/images/x.png`(인증 필요 이미지 경로는 D4의 경로 핸들러 — 투영 파일명 목록에 없으면 원본 유지).
4. **위키 폴더 밖 `../../manuals/*.md` 링크**(Home·04·70의 3개 문서) — 생성기가 `library.generated.ts`의 `LIBRARY_DOCS`에서 `file` 경로로 매칭해 **`/library?doc=<libraryId>`로 재작성**하고, 매칭에 실패하면 링크를 평문으로 강등한다(생성기가 결정하고 투영에 기록 — 렌더 시 추측 없음). /library 페이지는 마운트 시 `?doc=` 쿼리를 읽어 해당 문서를 연 상태로 시작하는 훅 하나만 추가된다(수정은 소폭, /library의 다른 동작 불변). 매뉴얼 문서를 위키가 다시 풀어쓰는 것이 아니라 문서 허브로 연결하는 것이므로 ADR-0108의 단일 표면 원칙과도 맞다.
5. **앵커 보존** — `page.md#anchor` 형태는 현재 원본에 없지만(실측 0건), 규칙상 해시는 재작성 후에도 그대로 붙인다. 페이지 내 순수 앵커 `](#...)`(53·54번에 실존)는 재작성 대상이 아니며, 이것이 작동하려면 아래 헤딩 id가 필요하다.

**렌더러 보강 두 가지**(marked v18 미지원, 원본 34개 문서가 쓰는 문법):

- **헤딩 id**: github-slugger 호환 슬러그(소문자화, 구두점 제거, 공백→하이픈, 한글 보존)를 붙이는 렌더러 오버라이드(또는 `marked-gfm-heading-id`). 실제 원본 앵커(`#m-a-필수-검증-여섯-가지`)가 재현되는지 생성기 때 검증한다(§5).
- **GitHub alert 변환**: `> [!NOTE]` / `> [!WARNING]` 블록인용을 콜아웃 컴포넌트(div + 라벨)로 바꾸는 사전 변환. 원본 문법은 GitHub에서도 통하므로 그대로 두고, 렌더층에서만 바꾼다.

**기각안**: 원본 마크다운의 링크를 미러용 스크립트로 미리 고치기 — 원본이 GitHub 위키 전제의 `.md` 링크를 유지해야 하므로 기각(2026-10-13 설계 §7.4 결정 유지).

### D6. 사이드바 등록 — 전역 사이드바에는 `/wiki` 하나, 페이지 안에 여정 그룹 왼쪽 열

- `lib/navigation.ts` "분석·참조" 구간에 `{ href: "/wiki", label: "사용 안내서" }`를 `/library` 뒤에 삽입한다: `/benchmarks`, `/library`, **`/wiki`**, `/glossary`, `/strategy`. 문서 허브(모든 문서) 다음에 사용자용 안내서가 오는 배치다.
- 위키 자체의 여정 내비는 **전역 사이드바에 주입하지 않고** `/wiki` 화면 안 왼쪽 열로 낸다(출처: `_Sidebar.md`의 그룹 구조를 생성기가 파싱해 투영). 전역 사이드바는 ADR-0105 SSOT의 화면 단위 등록만 담당한다.
- `tests/unit/navigation.test.ts`에 "분석·참조" 순서 고정 단언을 추가한다(현재는 이 구간 순서를 고정하는 단언이 없다 — 업무 구간과 ADMIN_NAV만 고정돼 있다). `/wiki/[slug]`는 NON_MENU_ROUTES 등재만으로 패리티를 통과한다.

### D7. 인증 — /library와 같은 표준 인증 읽기 화면

- 페이지는 AppShell 아래 렌더(루트 레이아웃이 모든 경로를 감싼다)되고, 데이터는 `/api/wiki`(목록+그룹), `/api/wiki/[slug]`(본문)에서 가져온다. 두 경로 모두 `authenticate(request)` 요구 — /library와 정확히 같은 자리.
- 이미지 경로도 `authenticate(request)`를 요구한다. 실측으로 성립하는 이유: `authenticate()`가 세션 쿠키를 받고(lib/auth.ts 125–141행), 같은 오리진 `<img>` 요청에 쿠키가 자동 실린다. Bearer-only였다면 `<img>`가 인증을 못 했을 것이다.
- AdminGuard를 붙이지 않는다 — 운영자가 아니라 **모든 로그인 사용자**가 읽는 안내서다.

### D8. 언어 — 위키는 한국어 로케일 존, 주변 UI 크롬도 한국어

`docs/wiki/ko/`는 2026-10-13 설계가 정한 한국어 로케일 존이고 각 페이지 frontmatter가 `lang: ko`를 선언한다. 뷰어가 더하는 UI 문구(내비 라벨 `사용 안내서`, 페이지 제목, 그룹 제목, 배지)도 앱 표준인 한글 평문으로 쓴다. 이 설계 문서 자체도 `lang: ko` + `lang_reason: source-material`로 등록한다.

## 5. 생성기 계약 (`scripts/co-newbiz/sync-wiki-projection.ts`)

**입력**
- `docs/wiki/ko/*.md` — 본문 페이지 36개 + `Home.md`. `_Sidebar.md`·`_Footer.md`는 페이지가 아니라 크롬 소스. `capture-manifest.json`은 캡처 도구 소유, 뷰어가 읽지 않는다.
- `docs/wiki/ko/images/*` — **파일명 목록만**(내용은 담지 않는다, D4).
- `app/web-next/lib/library.generated.ts` — 폴더 밖 `../../manuals/*.md` 링크의 `/library?doc=` 매핑용(D5 규칙 4).

**출력** `app/web-next/lib/wiki.generated.ts` — 하나의 체크인 생성물:
- `WIKI_PAGES: WIKI_PAGE_SUMMARY[]` — `{ slug, title, order, doc_type, stage, tracks, personas, verified_on }`. slug는 파일명에서 `.md`를 뺀 것, order는 숫자 접두(`Home`은 0), title은 첫 `# ` 헤딩. 정렬은 order → slug.
- `WIKI_CONTENT: Record<slug, { …summary, body }>` — **frontmatter를 벗긴 본문**. frontmatter 파싱은 라이브러리 생성기와 같은 `js-yaml`(루트 의존성)로, 벗기기는 생성 때 한 번(라이브러리처럼 렌더 시점에 하지 않는다).
- `WIKI_SIDEBAR_GROUPS: Array<{ group, items: Array<{ slug, title }> }>` — `_Sidebar.md` 파싱 결과. 굵은 줄(`**1. 공통 단계 (S1~S4)**`)이 그룹, 리스트 항목이 페이지. 파싱 검증: 사이드바의 모든 링크는 투영 페이지여야 하고(어기면 생성 중단), 사이드바에 없는 투영 페이지는 자동으로 말미의 `기타` 그룹에 붙여 어떤 페이지도 닿지 않는 고아가 되지 않게 한다.
- `WIKI_FOOTER: string` — `_Footer.md` 본문.
- `WIKI_IMAGE_FILES: string[]` — 정렬된 파일명 83개(D3·D4의 허용목록).

**멱등성·검증**
- 전면 재생성, 같은 입력이면 바이트 동일 출력(`readdir` 정렬 + 순서 고정 직렬화).
- `--check` 플래그: 스테일이면 exit 1(라이브러리 생성기와 같은 계약).
- 생성기 내장 검증: (a) 모든 폴더 안 `.md` 링크가 투영 페이지를 가리키는지, (b) 모든 `images/` 참조가 파일 목록에 있는지, (c) 페이지 내 앵커 링크(`#…`)가 같은 문서의 헤딩 슬러그와 일치하는지(github-slugger 호환 슬러그로 재현 — 53번 `#m-a-필수-검증-여섯-가지`, 54번 `#합작-조건-기록하기`가 첫 실측 케이스). 어기면 생성기가 페이지·줄을 밝히며 실패한다 — 렌더러를 원본에 맞추는 게 아니라 **원본 링크를 고치는 것이 SSOT 규율**이다.
- SSOT 불변: 생성기는 `docs/wiki/ko/`에 쓰지 않는다(읽기만).
- 호출 위치: 지금은 수동(라이브러리와 동일). 강제는 신설 드리프트 테스트 `tests/unit/wiki-projection-sync.test.ts`가 단위 스위트(/sync가 도는 자리)에서 한다 — 원본을 고쳤는데 투영을 재생성하지 않으면 테스트가 붉어진다.

## 6. 보안·권한

| 표면 | 인증 | 경로 안전 | 비고 |
|---|---|---|---|
| `/wiki`, `/wiki/[slug]` 페이지 | AppShell 인증 게이트(클라이언트) | slug는 화면 상태일 뿐, 데이터는 API에서 온다 | fs 접근 없음 |
| `/api/wiki`, `/api/wiki/[slug]` | `authenticate(request)` | 키 집합 조회, 없으면 404 | D3 — 클라이언트 통제 경로는 fs에 닿지 않음 |
| `/api/wiki/images/[file]` | `authenticate(request)`(쿠키로 `<img>` 성립) | `path.basename` 정규화 + 생성된 파일명 허용목록, 목록 밖은 404 | D4 |

- XSS 포즈는 /library와 동일: 렌더 대상은 저장소 커밋 문서뿐, 사용자 입력 경로 없음, `marked` CommonMark 렌더 + `dangerouslySetInnerHTML`(라이브러리 페이지가 이미 같은 근거로 사용).
- 위키는 읽기 전용 — 쓰기 경로(POST/PUT/DELETE)를 만들지 않는다. bearer 토큰의 scope와 무관하게 이 표면에는 변경이 없다.
- 이미지에 `X-Content-Type-Options: nosniff`를 더하고 `Content-Type`은 `image/png` 고정.

## 8. 범위 밖

- 위키 본문·캡처 내용의 수정(별도 흐름, 2026-10-13 설계의 갱신 절차 따름).
- GitHub 위키 미러링 자동화(원본의 `.md` 링크 규약은 유지, 미러 스크립트는 별도 과제).
- dev-sync 파이프라인에 위키(및 라이브러리) 투영 생성기 단계를 새로 추가하는 것 — 지금은 드리프트 테스트 강제로 충분하다. 반복 수동 갱신이 번거로워지면 별도 설계로 승격.
- 위키 내 검색, 읽기 위치 저장, 즐겨찾기, 인쇄용 뷰 — 뷰어가 쓰인 뒤 필요성을 다시 묻는다.
- 영어판 위키(`docs/wiki/en/`) — 존재하지 않는다.
- `capture-manifest.json` 소비 — 캡처 도구 체인의 소유다.
