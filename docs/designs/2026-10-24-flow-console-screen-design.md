## 2. 정보 아키텍처 (IA)

### 2.1 라우트 체계

```
/flows                          ← 메뉴 "분석·참조" 섹션 (navigation.ts SSOT에 등록, 패리티 테스트)
  ?tab=blueprint | ledger       ← Tabs 프리미티브(?tab= 쿼리 동기, ui-spec §1 3단계 내비 한도)
/flows/dry-run                  ← 드라이런 세션 목록 (NON_MENU_ROUTES 등록)
/flows/dry-run/[sessionId]      ← 드라이런 세션 작업 화면 (NON_MENU_ROUTES 등록)
```

### 2.2 결정: 드라이런 편집은 "전용 라우트"로, "활동별 드로어"로 하지 않는다

| 선택지 | 평가 |
|---|---|
| **(a) 전용 라우트 `/flows/dry-run/[sessionId]` — 채택** | (1) 세션은 오버라이드 편집·A/B 비교·선호 기록·제안 패널을 담는 **오래 사는 작업 대상**이므로 URL 고정·딥링크가 필요하다(벤치 A3-5 URL 공유 채택). (2) 화면의 주요 액션(드라이런 실행 — 비용 확인 수반)이 `PrimaryAction` 헤더 슬롯에 자리해야 하며, 드로어 안에서는 PrimaryAction 포털 구조(ADR-0121)와 3-depth 내비 한도가 모두 어긋난다. (3) AppShell의 드로어(SidebarDrawer)는 내비게이션 전용 패턴으로, 편집 폼을 담기 위한 선례가 없다. (4) 세션 비용 표시(§6.6)는 항상 보이는 헤더 영역을 요구 — 드로어는 스크롤에 묻힌다. |
| (b) 블루프린트 탭 안의 활동별 드로어 | 오버라이드 "편집"만이라면 가능했으나 A/B 비교 + 제안 패널 + 비용 확인을 드로어에 넣으면 밀도 붕괴. 드로어 안 드로어(행 확장 위) 포커스 함정 위험. |
| (c) 3번째 탭 "드라이런" | 탭은 이 화면의 두 읽기 축(설계/이력)을 나누는 수단. 드라이런은 쓰기 축이며 세션 단위로 탐색하는 별개 여정 — 탭에 넣으면 세션 목록·상세 두 층이 탭 하나에 겹쳐 3-depth 한도를 위반. |

**세션 목록의 위치**: `/flows`의 두 탭 아래 텍스트 링크("드라이런 세션 N건 →")와, 블루프린트 활동
드릴다운의 "이 활동 드라이런"(쓰기 게이트) 두 곳에서 `/flows/dry-run`으로 진입. 런 레저의 드라이런
행 칩(`dry_run_group_id`)에서도 해당 세션으로 점프한다(벤치 B1-2 그룹핑 변형 채택).

### 2.3 내비게이션 규칙 (ADR-0105)

- `NAV_SECTIONS["분석·참조"]`에 `{ href: "/flows", label: "플로우 콘솔" }` 추가 — 배치 순서는
  R&BD 전략 뒤(참조 성격)로 하고 `navigation.test.ts` 패리티가 강제한다.
- `/flows/dry-run*`는 `NON_MENU_ROUTES`에 등록(사이드바 없음, 브레드크럼 대신 화면 상단
  "← 플로우 콘솔" 복귀 링크). `/agents`가 NON_MENU_ROUTES에 머무는 기존 결정은 유지.

## 3. 공통 골격

- `main > h1` + `p.objective`(기존 문장 패턴) — h1: "플로우 콘솔", objective: "설계된 PM 에이전트
  플로우와 런 장부를 추적합니다 — 모든 AI 산출물은 제안 전용이며 게이트 결정은 사람이 기록합니다."
- 섹션 = `market-section` + `SectionToolbar`(title/filters/structure 준수, design-tokens).
- 표 = `data-table table-fixed-pct tmin-XX` + `ColGroup`(열비율 상수를 화면 파일에 `X_COL_PCT`
  로 선언 — /agents, agent-runs 선례) + `table-scroll`(role=region, tabIndex=0, aria-label) 래퍼.
- 상태 = `PageState`(loading/empty/error 단일 표면, ADR-0121). 페이지 상단 단문 role=alert 난립 금지.
- 차트 = `EChart` 래퍼(`role="img"` + ariaLabel) + **데이터 테이블 대체를 항상 인접 배치**(§6.5 요구).
- 토스트 = 변경 성공/실패에 `useToast`(결과 피드백 큐).

## 4. 블루프린트 뷰 (J1 — 설계된 플로우 파악)

### 4.1 레이아웃

데이터 소스: `pm-catalog.generated.ts` + `spec-activities.generated.ts` 생성 프러젝션(§6.2) — 렌더 시점 LLM 없음.

1. **단계 요약 그리드 (상단)** — S1–S12 각 단계를 한 칸으로: 단계 번호·명, 활동 수, 트랙 배지
   (greenfield/brownfield/공통), 최근 7일 오류 카운트(런 레저 API 집계). 상태는 색+텍스트
   (벤치 B2-1 히트맵의 "변형 채택" — 히트맵 색만은 WCAG 위반이므로 텍스트 카운트가 정보의 주체).
   단계 칸은 `<details>`가 아니라 버튼 목록 — 클릭 시 아래 활동 표가 해당 단계로 필터된다.
2. **활동 표 (하단)** — 기본은 전체 활동(트랙 필터 칩: 전체/greenfield/brownfield), 단계 선택 시
   해당 단계 활동만. 열: 활동 | 단계 | 에이전트 | 프롬프트 키·스킬 | 트랙 | 드라이런.
   행 클릭/Enter → **행 인라인 확장**(벤치 A1-1 변형 채택): 활동 상세(용도, 소스 프롬프트 키 목록,
   스킬 키, 동적 항목 여부, 최근 런 3건 요약 + "런 레저에서 보기" 링크).
3. **동적 항목 표기** — `agent: null` 프롬프트 2개(`s8.business_case_prose`, `committee.position`,
   §6.2)는 에이전트 열에 `동적 항목` 칩(status-gray) — 실행 시점 호출자 선언으로 귀속됨을
   표의 각주 문장으로 한 번 더 설명.

### 4.3 상호작용·상태

- 확장은 네이티브 `<details><summary>`(키보드 내장, 벤치 A1-3의 T/D 전역 단축키는 **기각** —
  네이티브 요소로 충분하고 v1 단축키 등록 표면을 만들지 않는다).
- "드라이런 시작" 버튼: 쓰기 권한(analyst+)에서만 활성. viewer는 PrimaryAction의
  viewerBlocked 이유 문구 표시, admin은 애초에 화면 접근 불가(§9 403).
- LLM 미구성은 **블루프린트 뷰에 영향 없음**(카탈로그는 생성 시점 산출물) — 런 레저·드라이런에만 상태가 나타난다(§5.4, §6.6).

## 5. 런 레저 뷰 (J2 — 수행 이력 추적)

### 5.1 필터 세트 (고정, 벤치 B1-1 채택 / A5-4 Columns 기각)

`FilterChip`(aria-pressed) + select 조합, URL 쿼리 동기:

- `agent_key` (select — 카탈로그 에이전트 목록)
- `entity` (텍스트 검색 — opportunity/project id·이름)
- `ok` (FilterChip 3상: 전체 / 성공만 / 실패만)
- `드라이런 제외` **기본 ON**(§6.6 "운영 대시보드는 기본적으로 제외") — 해제 시 `is_dry_run=true`
  런이 포함되고, 드라이런 행은 칩으로 구분된다.
- 기간(최근 24시간/7일/30일)

### 5.2 요약 카드 + 타임라인 (벤치 A5-1, A2-1 채택)

- 요약 카드 4장(선택 기간 기준): 호출 수 · 오류율 · 토큰 합 · 비용 합. 오류율>0은 적색 수치
  + "오류" 아이콘 텍스트(색 단독 금지).
- EChart 타임라인 1장: 기간별 호출 수(막대) + 비용(선, 보조축). `ariaLabel` 지정 + 아래
  `<details>표로 보기</details>`로 동일 데이터 테이블 제공(§6.5 EChart 대체 요구).

### 5.3 런 표와 계층 확장 (벤치 B3-1 채택, A1-1 변형)

커서 페이지네이션(limit+before, admin audit-log 패턴 §6.5 — "이전 런 불러오기" 버튼 1개).

```
┌ 런 레저 ──────────────────────────────────────────────────────────────────┐
│ [카드: 호출 1,204] [카드: 오류율 0.8% ▲] [카드: 토큰 3.2M] [카드: 비용 $18.4]│
│ [EChart: 기간별 호출수·비용]  ▸ 표로 보기(데이터 테이블 대체)                 │
│ 필터: agent (전체▾)  entity (____)  (성공만)(실패만)  (☑드라이런 제외=ON)     │
├───────────────────────────────────────────────────────────────────────────┤
│ 시각        │ 런/활동          │ 에이전트     │ 근거칩      │ 상태   │ 비용   │
│ 10-24 09:12│ op#123 S3 스케치  │ market-intel│ [카탈로그]   │ ✓성공  │ $0.012│
│            │  ▾ 확장: activity→agent→llm_call                             │
│ 10-24 09:02│ pj#45 S8 사업타당 │ (동적 항목)  │ [카탈로그]   │ ✕실패  │ —     │
│ 10-24 08:55│ op#121 S2 관련후보│ pm          │ [AI 폴백]칩  │ ✓성공  │ $0.003│
│            │   └ 드라이런 행: [드라이런]칩 + [세션 dr_7f3a로 이동]           │
│                                   [이전 런 불러오기] (커서)                 │
└───────────────────────────────────────────────────────────────────────────┘
```

**확장 행** (단일 `<td colspan>` 안의 정의 목록 + 소형 표, A1-2/A1-3 메타 행 채택, A5-5 토큰·비용 라인 채택):

```
│  ▾ activity_run: S3 스케치 — process_run pr_88 · 시작 09:12:03 · 완료 09:12:41 (38s) │
│     ├ agent_run: market-intel — agent 메타(classifiedBy=카탈로그, purpose=…)          │
│     │   ├ llm_call: gpt-… · latency 21.3s · tokens 4,120 in / 890 out · cost $0.0118 │
│     │   │   └ context(meta_json)·오류(null) — "렌더된 입력" 확인용(벤치 B2-4 변형)      │
│     │   └ llm_call: … (폴백 포함 모든 호출 행 — ok=false 행은 ✕ 텍스트+적색)           │
│     └ [런 레저 상세에서 이 런 전체 보기 →]                                             │
```

- **근거 칩 (classifiedBy)**: `카탈로그`(status-gray) / `규칙`(status-not-started) / `AI 폴백`
  (status-info) — /agents 페이지의 classifiedBy 칩 관행 확장. §6.3의 3값 표시.
- 드라이런 행: `드라이런` amber 칩 + 세션 링크(벤치 B1-2 그룹핑 변형). 세션 칩은 런 레저가
  필터 OFF일 때만 노출(기본 ON이라 숨겨져 있음을 칩 툴팁으로 설명).
- 상태 열: `✓성공`(green) / `✕실패`(red, role 아님 — 읽기전용 칩) — 아이콘+텍스트 병기(§6.5).
- EChart 런 상세 지연 막대: 확장 행 안에 인라인 차트는 넣지 않는다(밀도·접근성) — 런 단위
  activity별 지연 비교는 런 상세(별도 읽기 표면 아님, 확장 행의 "전체 보기")에서 EChart 가로
  막대(미니 간트, 벤치 B1-1/A2-1 채택) + 데이터 테이블 대체로 제공.

### 5.4 상태

| 상태 | 표현 |
|---|---|
| 로딩 | `PageState state="loading"` 스켈레톤 |

## 6. 드라이런 편집기 — `/flows/dry-run/[sessionId]` (J3 — 안전한 실험)

### 6.1 화면 구조 (상→하)

1. **세션 헤더**: 세션 ID(코드 스타일), 대상 활동(블루프린트 링크), 생성 시각, 상태 칩
   (편집 중/실행 중/완료), **세션 비용·토큰 누계 바**(벤치 B3-3, A5-5 채택 — §6.6 "세션당
   비용 표시"). PrimaryAction = "드라이런 실행"(비용 확인 수반, 화면의 유일 filled 버튼).
2. **오버라이드 편집기 (좌열)** — 단일 활동 단위(§6.6 v1). 편집 축 2개만:
   - 프롬프트 본문 텍스트에어리어(원본 위에 diff 표시)
   - 에이전트 재배정 select — **로스터에 존재하는 키만**(카탈로그/로스터 검증, 존재하지 않는
     키 저장 불가 §6.6 (1)). 모델·온도 파라미터 편집은 **기각**(벤치 §2.1 C공통 — SSOT 소유).
   - 저장 = 세션 스코프만. "SSOT에는 반영되지 않습니다" 안내 문장 상시 노출.
3. **A/B 비교 (우열)** — base(카탈로그 원본, 고정) vs override(벤치 A1-6 변형: 소스 지정 불필요).
   각 열: 프롬프트 diff + 최근 실행 결과 diff + 등급 필 `개선/악화/동률/미판정`(벤치 A3-2, A1-5
   채택 — 색+텍스트 병기). 결과 행별 선호 기록(썸업/다운 + 비고 한 줄, 벤치 A3-3 변형 →
   골든셋 시드 §6.6 (3)).
4. **AI 제안 패널** — §7과 동일 컴포넌트를 세션 컨텍스트로 임베드.
5. **실행 기록**: 이 세션의 드라이런 런 목록(dry_run_group_id 그룹핑, 벤치 B1-2 변형) —
   재실행은 기존 결과를 덮지 않고 새 런으로 적재(벤치 A3-3u 변형).

```
┌ 드라이런 세션 dr_7f3a ──────────────────────────── [세션 비용 $0.041 · 토큰 21k] ┐
│ 대상: S3 스케치(s1.sketch_draft) · 상태 [편집 중]        ← 플로우 콘솔로        │
│  (주요 액션 슬롯)                              [ 드라이런 실행 — 비용 확인 ]      │
├──────────────────────────────┬────────────────────────────────────────────────┤
```

### 6.2 실행 전 비용 확인 (§6.6 요구)

ConfirmDialog(ADR-0082): 예상 토큰·비용(직전 동일 활동 런의 실측값 기반) + "드라이런 호출은

버튼 옆에 — PrimaryAction 계약).

## 7. AI 제안 패널 (J4 — 개선 제안 수용/기각)

§6.7 제안 전용. 제안 생성 호출 자체가 `pm.flow_suggest` 카탈로그 활동으로 관문+장부 통과.

- **제안 카드** (`sizing-grade-card` 재사용): 유형 칩(`프롬프트 개선`/`에이전트 재배정`) +
  목적 한 문장 + **근거 블록**(최근 실패 런 N건 링크·산출 요약 — 벤치 A1-5 "개선 근거" 정신,
  런 레저 딥링크로 검증 가능하게) + 제안 내용(프롬프트 diff 또는 재배정 전후 키).
- **수용 affordance**: "수용" 버튼 = **이 세션의 오버라이드에 적용**만 수행(§6.7) — 적용 후
  세션 A/B 비교에 override로 반영되고 토스트로 확인. "기각"은 카드 상태만 세션에 기록.
- **제안 전용 칩**: 모든 카드에 `제안 전용` amber 칩(/agents 표면과 동일 칩 — 경계 #2 일관성).
  저장소 반영 경로는 카드 하단 한 줄 안내: "영구 반영은 제안 패키지(저장소 PR)로만 가능합니다."
- 수용이 만드는 것은 오버라이드일 뿐이며, A/B 비교와 선호 기록(J3)이 곧 수용의 검증 장치다.

```
┌ AI 제안 (2건) ──────────────────────────────────────────── 모두 제안 전용 칩 ┐
│ ┌───────────────────────────────────────────────────────────────────────┐ │
│ │ [프롬프트 개선] 스케치 초안의 산출물이 표 형식 누락으로 실패 3건          │ │
│ │ 근거: 실패 런 3건 보기 → (런 레저 딥링크)                                 │ │
│ │ 제안: "표 형식 지시문" 블록 추가 (diff 미리보기)                          │ │
│ │                                    [수용 → 오버라이드 적용]  [기각]       │ │
│ └───────────────────────────────────────────────────────────────────────┘ │
│ ┌ [에이전트 재배정] … [수용][기각] ┐                                        │
│ └ 영구 반영은 제안 패키지(저장소 PR)로만 가능합니다. ───────────────────────┘ │
```

## 11. 반응형·상호작용 규칙

## 12. 성공 기준 (측정 가능 — UX 독트린 인도물 계약)

1. **J1**: analyst가 "활동 X는 어떤 에이전트·프롬프트 키로 돌았나"를 블루프린트에서

2. **J2**: 특정 기회/프로젝트의 실패 런을 런 레저에서 **필터 2개 이내**로 좁히고, 그 런의

3. **J3**: 드라이런 실행 버튼은 **항상** 비용 확인 대화상자를 통과하며, 세션 비용이
   실행 전·후 모두 화면에 표시된다. 드라이런 결과가 비즈니스 테이블에 기록되는 경로는 0개
   (경계 테스트, §6.9).
4. **J4**: 제안 "수용"이 만드는 변화는 세션 오버라이드뿐이다 — 저장소 파일 쓰기 경로 0개
   (코드 검토·테스트로 단언).
5. **A11y**: §9 체크리스트 A1–A10 전부 통과(수동 체크리스트 + accessibility-audit 스킬 가용 시 자동 감사).
6. **내비**: `navigation.test.ts` 패리티 통과 — /flows는 메뉴 항목, /flows/dry-run*은 NON_MENU_ROUTES.

## 13. Rows 3–6 구현자를 위한 미해결 질문

1. **런 레저 API 응답에 `llmConfigured` 플래그 포함 여부** — LLM 미구성 empty 문구 분기를 위해
   `GET /api/flows/runs`가 시스템 설정을 함께 반환해야 하는지(Row 3 API 설계자 결정).
2. **예상 비용 산출 근거** — 실행 전 비용 확인(§6.2)의 "직전 동일 활동 런 실측값"이 존재하지
   않는 첫 실행의 기본값(상한 추정치? 보수적 상한?) — Row 4 드라이런 구현자 결정.
3. **세션 TTL 표시** — `dry_run_session` TTL 정리(§6.8)를 UI에서 "만료 예정" 칩으로 알릴지.
   벤치에 대응 패턴이 없어 v1 미포함으로 설계했으나, TTL이 짧다면 세션 목록에 만료일 표기 권장.
4. **확장 행의 접근성 상한** — 활동→에이전트→llm_call이 3단계 이상 깊어지는 체인 런(§6.10
   비목표의 전체 체인 드라이런이 후속으로 올 때)은 인라인 확장으로 부족할 수 있다 — 후속
   로우에서 런 상세 별도 라우트(`/flows/runs/[id]`) 재검토 여지.
5. **선호 기록의 스키마** — 골든셋 시드(§6.6 (3))가 선호(썸업/다운+비고)를 어떤 필드로 저장하는지
   (`dry_run_session` 테이블 설계와 함께 Row 3 마이그레이션 담당 결정). UI는 자유 텍스트 비고
   1줄 + 3상(선호/비선호/무판정)을 가정해 설계했다.
6. **Columns 커스터마이즈 재검토 트리거** — 벤치 A5-4를 기각했으나, 운영 3개월 뒤 필터·열 요청이
   반복되면 Weave식 Columns 버튼을 후속 설계로 재상정할 것(벤치 §2.1 재검토 조건과 연결).
