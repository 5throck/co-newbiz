# Sim Engine Runtime Separation + Independent Parallel Execution Layer

- Spec ID: `2026-09-19-sim-engine-runtime-separation`
- Date: 2026-09-19 (rev.2 — 검토 의견 P1/P2/P3 전면 반영 + 독립 병렬 실행 계층 추가)
- Status: **Proposed** — 초안. 구현은 단계별(§5)로 각각 별도 승인 후 착수한다.
- Origin: 성장율 격차 보정 루프(2026-09-18-s1-growth-gap-calibration)의 반복
  작업 효율화 논의. 사용자 제안 — 몬테카를로 GPU 엔진 분리·산업 분석 활용,
  및 "병렬 처리는 기능에 무관하게 독립적인 구조" 지시(2026-09-19).
- Review: 2026-09-19 AI 리뷰(P1 방법론 3건·P2 권고 3건·P3 참고 4건)를 반영해
  rev.2로 개정. 판정선 ≤15%는 사용자 조정(2026-09-19).

## 1. 배경과 병목의 정확한 위치

보정 루프의 1사이클은 (수용 → 재실행 → 격차 비교)이고, 재실행 비용은
**LLM 호출 체인**에 있다(산업당 수 분, 사이클2 실측: 2개 산업 순차 약 10분).
GPU는 이 체인을 가속하지 못한다. 따라서 이 문서는 서로 독립인 두 가지를
다룬다:

- **A. 반복 속도** — 기능과 무관한 독립 병렬 실행 계층(§3). 산업 N개 재분석을
  동시에 돌려 사이클 시간을 N배 가까이 줄인다. 이것이 속도의 레버다.
- **B. 수치 품질** — sim_engine 공용 런타임 분리(§4). 드라이버 impact 조합의
  확률론적 탐색(역산 feasibility)과 보정 후 CAGR 밴드의 불확실성 정량화.
  속도가 아니라 표현력·품질에 기여한다.

## 2. 스윕 방법론 (P1 보완 — 구현 승인의 전제)

스윕의 목적은 참조치에 추정을 맞추는 것이 **아니다**. 목적은 **역산
feasibility 뷰**다: "외부 참조에 도달하려면 어떤 드라이버 조합이 필요한가,
그중 우리가 믿을 만한 조합은 존재하는가."

- **표집 분포**: 수용된 드라이버의 `impact_pct`는 점 추정이다("±"는 방향
  표기). 기본 규칙 — 점 추정의 **±50% 삼각분포**(하한 0 보장). 제안
  스키마에 `spread_pct`(선택)를 추가해 LLM이 근거 신뢰도에 따라 폭을 넓힐 수
  있게 하나, 없으면 기본 규칙이 채운다.
- **드라이버 상관**: 실제 드라이버는 상관된다(그린수소 정책↔수전해 수요,
  AI 수요↔단가 하락). v1은 ① **개연성 필터** — 합산 impact가 필요 상향의
  2배를 초과하는 조합은 개연성 밖으로 제외, ② 상관 그룹 태그(선택) — 그룹
  지정 시 그룹 내 완전동조(copresence) 표집. 상관행렬은 후속 버전.
- **참조 불확실성**: 참조는 틀릴 수 있다 — 휴머노이드 5개 기관 전망이
  17.5~50.4%로 흩어진 것이 실측 증거. 기관 간 분산을 스윕의 입력
  불확실성으로 명시하고, 참조 다기관 중앙값 갱신 시 재스윕을 권고 표기.
- **feasibility 근거(실측)**: 연료전지 — 미수용 제안 합산 15.5%p vs 필요
  상향 8.8%p(17.5→26.3). 휴머노이드 — 수용 4건 합산 32.7%p vs 26.2%p 필요.
  두 산업 모두 feasible region이 존재한다.

## 3. 독립 병렬 실행 계층 (기능 무관 — 사용자 아키텍처 지시)

**원칙**: 몬테카를로/스윕, 산업 재분석, 프로필 재분석 등은 모두 "작업
제출자"일 뿐이다. 병렬 실행·동시성·재시도·관측은 **계층이 소유**한다.
기능이 계층 내부를 알지 못하고, 계층은 기능 종류를 모른다(비순환).

**구성**:

- **작업 정의**: `{kind, payload, resource_class, timeout_sec, retry}`.
  resource_class는 `llm` / `web` / `numeric` — 클래스별 동시성 상한을
  독립 관리한다(LLM은 대기 병목이라 상한 완화가 효과, web은 폴백 체인
  보호를 위해 제한적).
- **저장**: DB 기반 작업 테이블(`execution_job`, §6). 현재 재분석 작업 상태가
  in-memory Map(재시작 시 소실 — 확인된 기존 결함)인 것을 대체한다.
  "앱 수명 타이머는 앱과 함께 죽는다"는 watch:run 설계 규율(ADR-0019)과
  정렬. 기존 `analysis_task`는 프로젝트 인도물 검토용이라 재사용하지 않는다.
- **러너**: 자식 프로세스로 작업 실행(산업 3건 순차 ~15분 → 동시 ~5-6분),
  완료·실패·경과를 작업 테이블에 기록. 실패 재시도는 계층이 한다.
- **SQLite 제약(설계 전제)**: SQLite은 단일 writer — 워커는 연산만 하고
  쓰기는 짧은 트랜잭션 + WAL/busy_timeout으로 직렬화한다. 동시 쓰기
  테스트를 검증 항목에 포함한다(§7).

**효과**: 보정 사이클 오케스트레이터(§5 3단계)가 이 계층 위에서 동작해
산업 N개 재분석이 자동 동시 실행되며, 이후 어떤 장기 작업(경쟁사 프로필
일괄 재분석 등)에도 동일 계층을 재사용한다.

## 4. sim_engine 공용 런타임 분리 (P2 반영)

### 경계와 정당성

- `python/sim_engine/`을 독립 패키지로 승격: `device.py`(CUDA/MPS/XPU/ROCm
  자동감지, CPU numpy 폴백, GPU_WORK_THRESHOLD 200k), 실행 큐, 결과 직렬화.
- 웹앱은 **서브프로세스로 호출**(기존 structure-simulation → structure_sim.py
  패턴 준용). 앱 번들에 torch를 넣지 않는다.
- **GPU 적합성 정정(rev.2)**: 드라이버 스윕의 실규모는 k≤10 × N≤10만 =
  CPU numpy 수십 ms다(`GPU_WORK_THRESHOLD` 하단). "GPU 적합"이 아니라
  **분리의 정당성은 공용 런타임·재사용**에 있고, GPU는 밴드 몬테카를로
  확장 단계의 **선택 사항**이다.

### 산업 분석 연결점

- `POST /api/market-overview/industry/[industryId]/calibration-sweep`:
  §2 방법론으로 조합을 표집·집계해 역산 feasibility 뷰를 반환. 스윕은
  **다음 재분석 제약 주입 이전**에 실행한다(실행 순서: 스윕 → 재분석 제약
  → 격차 재측정).

### 저장 계약 (P2)

- 신규 `calibration_sweep_result` — **분위수 요약만 저장**: P10/P50/P90
  도달 격차, 드라이버별 기여 분위수 JSON, 표본 수, plausibility 필터
  제외율, device(cpu|cuda|mps|xpu|rocm), created_at. **원시 표본은 미저장**.

## 5. 판정선·에스컬레이션·단계 (P3 반영)

### 판정선 — 이력현상(hysteresis) 설계

- **트리거(발동)**: 기존 `CALIBRATION_TRIGGER_PCT = 20%` 유지 — 격차 ≥20%
  시 보정 루프·드라이버 귀인 시작.
- **판정선(수렴·종료)**: 신규 `CONVERGENCE_TARGET_PCT = 15%` — 격차 ≤15%
  도달 시 스윕 종료·수렴 판정 (사용자 조정 2026-09-19, 초안 20%에서 하향).
- 15~20% 밴드는 **"진행 중(발동됐으나 미수렴)"** 상태로 정의한다 — 트리거와
  판정선의 분리는 경계값 근처에서 사이클이 켜졌다 꺄졌다 하는 진동을 막는다.
  두 상수는 문서·코드에서 명확히 구분해 관리한다.
- **에스컬레이션**: 3사이클 후에도 ≤15% 미도달이면 **결정론 CAGR 스케일링
  에스컬레이션을 사람 결정 트리거**로 올린다(기존 유보 항목과 연결 — 자동
  적용 아님, 경계 #2).
- 현 데이터(2026-09-19): 휴머노이드 55.6%·연료전지 33.5% — 두 임계 모두
  상회, 다음 사이클 지속 대상.

### 단계별 추진 (각 단계 별도 PR·별도 승인)

1. **독립 병렬 실행 계층** — `execution_job` 마이그레이션, 러너, 어댑터
   인터페이스, 산업 재분석 어댑터(증명용 1종), 동시성/재시작 테스트.
   반복 속도의 레버이자 이후 단계의 기반이므로 최우선.
2. **sim_engine 패키지화 + 스윕** — 패키지 경계 이동(기존 인터페이스 유지),
   `calibration-sweep` API + `calibration_sweep_result`, 수학 단위 테스트.
3. **오케스트레이터 + 밴드 MC** — 사이클 원클릭(계층 기반: 수용 확인 →
   병렬 재분석 → 격차 비교표 갱신), CAGR 밴드 P10/P50/P90(GPU 선택),
   에스컬레이션 트리거 연결. 무한 자동반복 없음 — 사이클 단위 보고 후 사람이
   계속 여부를 결정한다(경계 #2).

## 6. 스키마 (1단계 마이그레이션)

`execution_job`: id, kind, payload_json, resource_class CHECK(llm|web|numeric),
status CHECK(queued|running|succeeded|failed|cancelled), attempt, max_retry,
timeout_sec, locked_by, locked_at, result_json, error, created_by, created_at,
updated_at. 인덱스: (status, resource_class, created_at).

`calibration_sweep_result`(2단계): id, industry_id, version_no,
driver_set_hash, p10/p50/p90_gap_pct, per_driver_quantiles_json, sample_count,
plausible_ratio, device, created_at.

## 7. 검증 (P3 — 문서에 명시)

- 스윕 수학: seed 고정 결정론(동일 입력 동일 분위수), 분위수 정확성
  (기지분포 복원), 개연성 필터 제외율, 삼각분포 경계(하한 0).
- 병렬 계층: 동시 실행 상한 준수, 재시작 후 queued 작업 복귀(in-memory
  대체 증명), 실패 재시도, SQLite 동시 쓰기 직렬화(WAL/busy_timeout 하에서
  교착 없음).
- CPU 전용 경로: GPU 부재 환경 강의 테스트(device 폴백, 경고 기록).
- CI는 CPU 경로 필수 통과(§P2 거버넌스).

## 8. 거버넌스 (P2)

- L0/L1 스크립트 전파 규율과 공존 — sim_engine 승격은 전파 대상 목록 갱신과
  함께 수행.
- `requirements-gpu-*.txt`는 GPU 배포에서만 선택 설치. 기본 설치·CI는 CPU.
- 각 단계 종료 시 이 문서의 Status/단계 표기를 갱신한다.

## 9. 명시적 한계

- 루프 병목은 LLM 호출 체인 — 본 분리의 속도 기여는 병렬 계층(§3)에서만
  나온다. 스윕은 품질·표현력 향상이다.
- GPU가 없는 배포에서 CPU numpy로 열화 없이 동작한다(device.py 계약).
- 참조 편향 경계: 스윕 결과는 "참조 달성 가능성"의 분석 자료이며, 참조치가
  옳다는 전제가 아니다(§2).
