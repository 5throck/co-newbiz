## 3. R2-A decisions

### 3.1 New market analysis (items 1 and 2)

- `/market?new=1` renders the S1 screen with the new-industry form open, scrolled into view and focused. It is never auto-redirected into an unrelated deal. The industry master is global, so the analysis needs no deal.
- The board primary `＋ 새 검토 시작 (시장분석부터)` links to `/market?new=1`. Path: board click 1, type the name, `분석 범위 선택` click 2, `이 산업만 분석` click 3.
- Picker pages `/market`, `/opportunities`, `/synergy`, `/route-decision` (and `/greenfield`, `/brownfield`) share one layout: breadcrumb, h1, a create action as the primary, an explanatory line, then the deal list. Create actions: market `새 시장분석 시작`; opportunities `새 기회 등록` (`/opportunities?new=1`); synergy `그룹·계열사 프로파일 등록`; route-decision, greenfield, brownfield `새 검토 시작 (시장분석부터)` (S3 to S7 need a deal that already passed S1 and S2).
- The sidebar marks `검토/안건 보드` active on the deal-less flat routes (`DEAL_FLOW_FLAT_ROUTES` in `lib/navigation.ts`) and the topbar gives them a contextual back to the board.

### 3.2 Stage rail S8 to S12 (item 3)

`/deals/{id}` carries the opportunity id; S8 to S12 need the project id. `useDealContext` reads `project_id` from the opportunity (requests are de-duplicated for 3 s). A promoted deal links to `/projects/{project_id}/...`. An unpromoted deal shows those stages as non-links (`aria-disabled`, a visible `승격 후` label and a title with the reason); an unresolvable deal says so. The handoff strip uses the same resolver.

### 3.3 S3 (item 4)

The empty state and the new-analysis form no longer refer to a non-existent `회사 등록` button. They state the order `그룹 → 계열사 → 시너지 분석` and link to the group/affiliate profile surface (`/deals/{id}/s3?surface=company`, or `/our-company` outside a deal). `분석 시작` stays disabled until a target is chosen and now shows the reason next to it with the same link.

### 3.4 S2 row action (item 5)

Each row advances its own opportunity: an identified row offers `매력도 평가` (opens the detail with the score field focused), an assessed or selected row offers `S3로 진행` (`/deals/{rowId}/s3`). The header primary names its target (`S3로: <기회명>`).

### 3.5 Back targets and breadcrumbs (item 6)

The opportunity detail's back goes to `/deals/{id}/s2` (`← S2 목록으로`); the topbar back for it reads `S2 기회 발굴`. The detail gets an h1, the breadcrumb and the stage rail. The S1 report gets the breadcrumb (`… › S1 시장분석 › <산업>`), the stage rail, `← 산업 목록으로` and the primary `다음: S2 기회 발굴 →`. The report heading is now the page h1.

### 3.6 Known target and orphan routes (items 7 and 8)

Known-target entry (`/opportunities?known_target=1`): the registration form is rendered at the top under an explanatory banner; its first field is focused. Guide steps on the opportunity detail are underlined links. Opening the form from `＋ 기회 등록` now also scrolls and focuses (walkthrough F9).

## 3b. R2-B decisions

### 3b.1 Shared gate-recording flow (items 1 and 2)

- One flow on every `GateDecisionPanel` (S5 to S11, so S8, S9 and both S11 gates included): the submit opens a confirm dialog that names the gate, the decision and the rationale; only the dialog's `기록` sends the request. After the response a toast confirms it, the form collapses into a `기록된 결정` summary (decision chip, time, rationale; no way to submit the same decision again), and a GO shows a next-stage link (S8 to `S9 실사·검증`, S9 to `S10 투자구조 설계`, Entity IC to the Group IC form, Group IC to `S12 사후 관리`). A HOLD keeps the form so the evidence can be completed and a new decision recorded; a KILL points to S12 closure. History stays append-only; correcting a decision is a new row.
- A submit that cannot proceed shows its reason as text beside the button (rationale missing, KILL without learning capture, HOLD without the missing-artifact list).
- The decision is reachable from the top: the stage primary action is `결정 기록 (사람)` (`GateDecisionJump`), which scrolls to the gate panel and focuses its first field. S8 has a `결정` tab, so the form is no longer repeated under every analysis tab; `밸류에이션 재계산` is a secondary button.
- The 3-stage review block shows once per gate: stage screens render the summary strip once at the top with the gate(s) in it (`fs`, `dd`, `entity_ic` plus `group_ic`) and the panels pass `showReview={false}`. S11 no longer repeats the block for Entity and Group IC.

### 3b.2 IC GO with missing artifacts (item 3)

Boundary #2: the system never blocks a human GO. `GET /api/projects/{id}/ic-package` returns `gates.go_gaps` (no adopted business case, RAG not graded, establishment steps pending for internal or joint origin). A GO on `entity_ic` or `group_ic` while the list is not empty opens an `누락 산출물 경고` dialog that lists each gap and requires a typed rationale (the confirm button stays disabled with a visible reason). The POST carries `gap_rationale`; the route re-derives the gaps itself (a client-supplied list is ignored), stores the rationale with the decision and answers `gap_override`. No schema change: the override is appended to `gate_decision.rationale` behind the `[누락 산출물 예외 근거]` marker (`lib/ic-gap-override.ts`) and parsed back on read, so gate history, the IC package (`gates.latest[].gap_override`, `gates.history[].gap_override`) and the S11 package section `누락 산출물 예외 근거` show it. The API itself stays non-blocking: the typed rationale is enforced on the screen, which is the only human surface (the process-governance-manager dissent, to block when nothing is adopted, is preserved; the condition to store and show the rationale is met).

### 3b.3 S8 (item 4)

On project pages the stage row (`요약 / 분석 / WACC / 재무분석`) is the only place for WACC and `재무분석`; the in-page tabs no longer repeat them (old `?tab=wacc` and `?tab=financial-analysis` links redirect to the stage routes). The embedded deal tab has no stage row, so it keeps them. The decision panel appears once, in the `결정` tab.

### 3b.4 S9 (item 5)

- Each checklist row has `면제 요청·연결`, which opens a dialog: link an already active waiver, or request a new one with the clause prefilled with `<checklist> <item>`. Non-waivable items (bf-01 to bf-03) print the reason on the row. While a judgement is being saved the whole group is locked and a visible `기록 중` line says why; a viewer sees a line explaining that the buttons need the analyst role.
- The waiver request form uses a wrapping grid (no overlap at 1280), a disabled `요청` shows what is missing, and below 640 px the checklist table becomes one card per row (no clipped buttons).
- The M&A checklist text is shown in Korean from a display catalog (`lib/dd-checklist-ko.ts`; ids, yaml and stored data unchanged; English source in the tooltip).
- `판정 대기` is the default for items without a judgement row (new items only). Existing judgements are grandfathered: they are displayed exactly as stored with `판정: <who> · <date>`, nothing rewrites or re-opens them, projects pinned before the predicate dates keep their counting, and `tests/unit/dd-grandfather.test.ts` asserts it. Row filters `전체 / 판정 대기만 / 미충족만` replace scrolling 100 rows.

### 3b.5 S10 (item 6)

One primary `투자구조 가설 기록` in the header: it opens and focuses the hypothesis form. The in-form `가설 기록` is the submit and shows why it is disabled. Two tab levels (stage row plus the in-page tabs). Stake and payment-method values are shown in Korean (`과반 지분`, `신주·구주 혼합`); `수표 믹스` is now `지급 수단 구성`.

### 3b.6 S11 (item 7)

Each establishment step has an owner column (the person who recorded it, `미지정` before) and an action `증적과 함께 완료`: an inline form (status, evidence URL or note, required to complete) that goes through the confirm dialog; only a person can do it, an agent cannot. Steps already done show `완료됨`. The PMI kickoff form disappears once a kickoff is recorded. The charter is linked from the S11 header (`프로젝트 추진계획(차터) 보기`); its page now frames itself as S12 (its tab group), so the tagline no longer reads the S8 line `돈이 되는가?`.

## 3c. R2-C system quality

Axe baseline on 70 route instances (analyst app routes plus admin console), `tests/scenarios/axe-sweep.test.ts`: before R2-C, light 3 serious nodes (3 violations), dark 136 serious nodes (48 violations); after, light 0 and dark 0.

### 3c.1 Dark-mode contrast at the token level (item 1)

The failures were token pairs, not per-page colours. `--primary-fg` (new) is the text colour on a solid `--primary` fill: white in light, near-black in dark. Dark `--primary-l` moves from 60% to 66% so primary text on tinted surfaces (current stage step, active tab) reaches 4.5:1, `--primary-dim` (chip text) is now lighter than the fill in dark (74%), and `--primary-strong` is a real token for the hover fill. `.btn-primary`, selected `.control-chip` and `.pager .pg.cur` read `--primary-fg`. Warning chips use `--amber-fg` on `--warning-bg`. `bun run contrast:check` enforces the new pairs (`--primary-fg` on `--primary` and `--primary-strong`, `--primary` and `--primary-dim` on `--primary-bg`, `--primary` on `--surface-2`) in both themes. The E2E sweep runs axe on every route in light and in dark (`html[data-theme=dark]` set after load) and asserts zero serious/critical.

### 3c.2 404 and error pages (item 2)

`app/not-found.tsx` and `app/error.tsx` render `components/StatusPage.tsx`: Korean copy, themed tokens, an h1, and three exits (`다시 시도` on errors, `검토/안건 보드로 이동`, `이전 화면으로`). Raw error messages are not shown; the digest sits in a `개발자용 상세` disclosure.

### 3c.3 Titles and h1 (item 3)

Every `page.tsx` now has a `layout.tsx` with `metadata.title` (server component; the root template adds `· 신규사업 검토`). The admin layout became a server layout around `components/AdminGuard.tsx`. The sweep asserts exactly one h1 and a non-default title on all 69 routes.

### 3c.4 390 px (item 4)

Below 640 px a `.data-table` scrolls inside itself, and buttons and status chips wrap instead of forcing the page wider. The sweep asserts no horizontal overflow at 390 px on every analyst route (the five offenders were `/brownfield`, `/greenfield`, `/projects/{id}/dd`, `/companies`, `/projects/{id}/wacc`; `/greenfield` was already fixed by R2-B).

### 3c.5 Class-less buttons (item 5)

`design:lint` rule 7 rejects a `<button>` with neither `className` nor a props spread (brace-aware, so arrow functions in handlers do not hide it). Fixed: `TabNav`, the synergy re-run button, the project-member remove button and the password-change submit.

### 3c.6 Accessibility residue (item 6)

`PageState` loading is `role="status"` with its label (fixes `aria-prohibited-attr`); `SourceTooltip` keeps its visible figure in the accessible name (`label-content-name-mismatch`); the inbox failure list is a `ul` inside the alert region (stray `li`); the risk heatmap notes use `--fs-caption` instead of 10 px.

### 3c.7 Synthetic and degenerate values (item 7)

`lib/synthetic-value.ts`: a version with any non-LLM step is synthetic (`isSyntheticSizing`); S1 summary tiles and the S2 industry chips show `합성 추정 (검증 안 됨)` beside the number (the insights API adds `synthetic`). CAGR at or below -99.5% and a size of 0 or below show `산정 불가`. The number is not hidden when a model did run (risk-officer's point): only unverified or degenerate values are marked.

### 3c.8 Label map and jargon (item 8)

`lib/labels.ts` is the one map for gates, decisions, tracks, DD domains and closure record keys, plus `localizeMessage` (applied to every API error in `lib/api.ts`) and `localizeRequirement` (stage requirement lists). Removed from reader-facing copy: `gate_decision(kill)`, `missing_artifacts`, `LLM provider is not configured`, `origin∈{...}`, `★ RECOMMENDED` (now `★ 권고안`), the unlabelled `FS` on WACC/business-case copy (`타당성 분석(FS)`), `Hurdle IRR` and `Run`, the DD tabs (`상업 실사`, `기술 실사`, `법무 실사`), IC history lines, the inbox `딜` (`검토/안건`), and the `/share` heading. ADR references moved into `DevRef` (a collapsed `개발자 참고` disclosure) or were dropped from visible text.

### 3c.9 Viewer and admin redirects (item 9)

`PrimaryAction` disables itself for the viewer role and prints `보기 권한만 있습니다` beside the button (`readOnly` opts out for navigation and read actions). A non-admin who opens `/admin/*` lands on the board with a `role="status"` notice (`?moved=admin`). The server stays authoritative: `tests/unit/viewer-write-guard.test.ts` sends a viewer (project member) through 33 write routes and asserts 403 from the role guard. It found two real defects: `deal-structure` and `charter` (and `charter/confirm`) answered a viewer with 400 `role_required`; they now answer 403.

### 3c.10 Error states (item 10)

`/proposals/{bogus}/confirm` renders `제안을 찾을 수 없습니다` (the 404-equivalent `StatusPage`). `/oauth/authorize` with missing or invalid parameters renders `연결 요청을 확인할 수 없습니다`, grants nothing, and links to the connected apps and the board; the server message stays under a developer disclosure.

## 5. Accessibility

- Breadcrumb is a `nav` landmark labelled `현재 위치` with an ordered list; the current page uses `aria-current="page"`; separators are `aria-hidden`.
- Disabled rail stages are `aria-disabled` spans with a visible text label (not colour alone) and a title; they are not focus stops. Row actions carry the opportunity name in screen-reader text (`매력도 평가 — <기회명>`).
- Focus management: entry forms receive focus after `scrollIntoView`; the moved-route notice is a `role="status"` region with a keyboard-reachable `닫기` button.
- Every touched page has exactly one h1 and a distinct document title (WCAG 2.4.2, 2.4.6, 2.4.8).
- Notice and banner colours use `--surface`, `--fg`, `--border`, `--accent`. Since R2-C the `--primary-*` tokens also pass in dark; every route is scanned in both themes: 0 serious/critical.
- Targets keep the 44 px mobile minimum through the existing `.btn-ghost`/`.back-link` rules.

## 8. R2-E partials (2026-10-09)

Closes the six remaining partials from `docs/reports/ux/2026-10-09-walkthrough-round2-verification.md`.

### 8.1 IC GO gap rationale — server-side agreement (finding 1, s8-s12)

The project gate-decisions POST now re-derives the open gaps at decision time
(`icGoGapItems`) and refuses an `entity_ic`/`group_ic` GO over open gaps without a
non-empty `gap_rationale` (`422 ic_gap_rationale_required`, message names the gaps).
The rationale is composed into `gate_decision.rationale` with the existing
`[누락 산출물 예외 근거]` marker — no migration; rows recorded before this change
are grandfathered untouched. The proposal path agrees: `gate_decision` payloads
(lib/proposals.ts, MCP `propose_gate_decision`) carry an optional `gap_rationale`
through confirm into the executed route, so an agent proposal cannot record a
gapped GO that the REST path would refuse. Existing rows are never rewritten.

### 8.2 Waiver per-row prefill — one-call body (finding 5)

POST `/api/projects/{id}/waivers` accepts `dd_item: {checklist_id, item_id}` in
place of a hand-built `clause_ref`; the route derives `clause_ref` as
`{checklist_id} {item_id}` and a default reason naming the item. `WaiverRequestForm`
sends the item identity directly (ddMode skips the clause/reason required-field checks),
documented in openapi.yaml §requestProjectWaiver.

### 8.3 S8 dual tab rows — IA decision (finding 4)

The stage-level row (lib/stage-tabs.ts) is authoritative: S8 primary tabs are
summary · scenario comparison · per-target selection · WACC · financial analysis, with
overview · generation · recommendation · parameters · snapshot · target costing · decision ·
risk heatmap under More (Korean labels per the stage-tabs map). The in-page second
TabNav row renders only in embedded mode (stage frames); page mode shows an
sr-only note instead. Old `?tab=` deep links (wacc/financial-analysis) redirect
in page mode. Recorded decision: one tab row per stage; page sub-tabs are
embedded-only.

### 8.4 Archive closure type (finding 11)

`/projects/archives` gains a closure type (`마감 유형`) column showing `md_project.closure_type`
via the shared `closureTypeLabel` (lib/labels.ts) — the same Korean wording as
ClosureModal, now sourced from one map (`CLOSURE_TYPE_LABEL`) so the list and the
modal cannot drift. The list payload already carried `closure_type`; no API change.

### 8.5 Star accessible name (finding F14)

The S1 industry pin button carries `aria-label` (pin/unpin labels naming the industry) with the existing `aria-pressed`. The walkthrough
pointed at S2, but S2 has no star control (its `aria-pressed` buttons are
filters) — the S1 accessible name is the actual defect fixed.

### 8.6 Legacy business-case notice (item 1)

Brownfield projects promoted before ADR-0143 hold `business_case_model` rows with
`target_id NULL`; the S8 predicate then reports "Business Case required" (`Business Case가 필요합니다`) with
no hint why. `countLegacyUnassignedModels` (lib/business-case-legacy.ts) counts
NULL-target models for shortlist-scoped projects and the S8 stage shows a labelled
warning notice (Onyx tokens, text not colour alone) naming the count and offering
per-target regeneration (`대상별 재생성`) as the primary action. Legacy models are never migrated, backfilled,
or auto-deleted.

### 8.7 R2-F — per-target regeneration and AI terminology (2026-10-09)

Per-target regeneration (user report: the legacy-notice regeneration button was a silent no-op): the
already-run idempotency guard in POST `/api/projects/{id}/business-case/generate`
returned the existing non-failed `s8_business_case_generation` run, so a project
holding legacy NULL-target models never generated per-target ones. The route now
accepts `{ regenerate: true }` which bypasses the guard and starts a NEW run —
still analyst+, still proposals-only (boundary #2). The legacy-notice primary
button and the recalculation ghost action send
`regenerate: true`; the ordinary dual-view generation path keeps the guard and,
when it returns `alreadyRun`, the UI says so with an explicit already-run message
pointing at the regeneration button instead of doing nothing. The existing
`load()` refetch makes the new per-target (`variant market_forward`, `target_id`
set) models appear. E2E coverage seeds a legacy NULL-target model plus a done run
and asserts the per-target models appear after clicking the regeneration button.

AI terminology decision: all user-facing display labels now read `AI chujeon`
(Korean for 'AI recommendation') for AI-generated suggestions/recommendations/drafts
(formerly the LLM qualifier and the AI-proposal label) and a plain `AI` qualifier for neutral ones
(estimation, analysis, brief, summary, monitoring, reliability). Status/technical wording:
'unconfigured' replaces the former LLM-not-configured phrasing. Zero "LLM" remains in user-facing strings across
`app/web-next/components` and `app/web-next/app` .tsx (title and aria-label
attributes included; JSX comments and stored source enums — `source: "llm"`,
`provenance: "llm-estimate"`, env var names — are unchanged display mapping only).
Labels never imply the AI decided: the recommendation wording is used, never a
decision wording (boundary #2).

## 9. R2-G — dark-mode native select popup legibility (2026-11-04)

User report 2026-11-04, dark mode only: a dropdown's popup background and text
color compute nearly identical — the selected item renders as a black block,
the other options are invisible. Light mode is unaffected. Gate record:
`docs/decisions/DEC-20261104-07.md`. All line cites below are pre-change,
working tree at `eb1ba9e0`.

### 9.1 Diagnosis (locked)

- `app/web-next/app/styles.css:279-296` styles the control
  (`background: var(--input-bg); color: var(--fg)` at `:292-293`) but **no
  `option`/`optgroup` rules are authored anywhere in the stylesheet**
  (grep-verified: the only "option" rules are the custom
  `.agent-combobox-option` listbox `:4442-4445`, which is correctly
  token-paired and is NOT a native select).
- Dark palette (`:167+`): `--input-bg: rgba(255,255,255,0.03)` (`:201`)
  composites to ≈ `#111317` over `--bg` `#0a0c10` (`:176`) — near-black;
  `--fg: #eef0f4` (`:177`); `color-scheme: dark` IS declared (`:168`).
- In Chromium-family browsers the native popup canvas takes the author-set
  control background, but item text colors are never authored, so each item's
  color falls to UA fallback resolution. When that fallback computes
  near-black on the near-black canvas, every item is invisible and the
  highlighted row reads as a black block. The failure is browser-version
  dependent because `color-scheme` propagation into the popup differs per
  release — which is exactly why the fix must not depend on it.

### 9.2 Decision — one global rule, both themes

The exact Row 1 change (mechanical paste):

```css
  select option, select optgroup {
    background-color: var(--surface);
    color: var(--fg);
  }
```

- **Placement**: inside `@layer base`, inserted directly after the
  `input, select, textarea` rule closes (`:295`), before the focus rule
  (`:297`). Element-selector base rules live in this layer per the `:231`
  comment — Tailwind preflight and future utilities must outrank them, the
  same reasoning as the heading rules at `:261-263`.
- **Token pairing** — `--surface` background + `--fg` text, justified against
  the Onyx ≥ 4.5:1 rule in BOTH themes (computed 2026-11-04, WCAG 2.1
  relative luminance): dark `#171b22` vs `#eef0f4` = 15.1:1; light `#ffffff`
  vs `#171a21` = 17.4:1. `--surface` is the elevated-surface token — the
  native popup is an elevated sheet, the same convention as the
  `.agent-combobox` listbox and notice surfaces (§5). `--bg` also passes
  (dark 17.2:1) but is the page canvas, not a popup surface. Text is `--fg`,
  not `--muted-fg` (which passes at 7.6:1 dark but would dim popup items
  below the closed control's own text for no benefit).
- **`option:checked` and hover highlight stay UA-managed.** Authoring checked
  colors is honored inconsistently across engines (Safari ignores most option
  styling; Chromium composites its own accent highlight under author colors),
  so a custom checked rule would introduce a second engine-dependent behavior
  rather than remove one. With item colors authored, the UA highlight remains
  a distinct, contrast-managed accent row in both themes. The reported defect
  is item legibility; the single rule closes it.
- **Explicitly not touched**: the custom `.agent-combobox-*` listbox
  (`:4436-4445`, already correct), ECharts, every other control. Disabled
  placeholder options (e.g. `EntryMarketFlow.tsx` version placeholder) keep
  UA dimming — no extra rule.

### 9.3 Scope note

The user did not name the screen. The fix is global for every native
`<select>` (30+ call sites: `GateDecisionPanel`, `CommitteePanel`,
`GateIntegrity`, `PromotionPanel`, `WaiverPanel`, the inbox deal filter, and
more). The only custom listbox in the app (`.agent-combobox`) is verified
correct, so if the reported dropdown turns out to be a different custom
widget on a specific screen, this amendment stands as the triage baseline and
that widget becomes its own finding.

### 9.4 Verification (manual protocol)

No unit or E2E test can assert popup rendering — the native popup is browser
chrome outside the DOM; axe and Playwright cannot see it. The bar is manual,
fails-before/passes-after, theme-toggled:

1. Run the app, open a screen with a native select, toggle dark via
   `ThemeToggle`.
2. Representative selects: the inbox deal filter
   (`app/inbox/page.tsx:121`), the S1 run-form version select
   (`components/EntryMarketFlow.tsx:310`, `data-testid="entry-flow-version-select"`),
   and the gate decision select (`components/GateDecisionPanel.tsx:665`).
3. Fails-before (reproduces the report): popup background near-black, options
   invisible, the selected row a black block.
4. Passes-after: every option renders `--fg` text on `--surface`; the
   selected item is legible before and during highlight; the hover/checked
   highlight is a distinct accent row.
5. Toggle light once to confirm no regression (the same pairing passes there
   at 17.4:1).
