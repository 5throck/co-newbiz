# 관리자 매뉴얼 — 시스템 관리자

> **언어**: [English](admin-manual.md) · **한국어**

**독자**: 시스템 관리자(리뷰 프로세스의 투자위원회 "administrator"와 다른 개념 — 여기서는 기술적 시스템 관리를 뜻한다)
**대상 아님**: analyst(`business-manual.md` 참조), 배치/백업 파이프라인을 일상적으로 운영하는 운영자(`operations-manual.md` 참조)

## 이 매뉴얼이 다루는 것

계정 관리, 규제 버전 관리, 마스터 데이터 관리, 외부 자료 출처의 키와 승인, 알림 rule 설정 — 관리 콘솔(`/admin`, `app/web-next/app/admin`)이 담당하는 업무.

## 1. 계정 관리

- **셀프 등록 → `pending` → 관리자 승인 → `active`.** 역할: `admin` / `analyst` / `viewer`.
- **비밀번호 초기화**: 사용자가 요청 → 관리자가 임시 비밀번호 설정 → 사용자의 다음 로그인은 다른 어떤 작업보다 먼저 비밀번호 변경 화면을 강제한다(`must_change_password`) → 새 비밀번호는 `password_history`와 대조해 재사용을 차단한다.
- **관리자는 사용자의 실제 비밀번호를 절대 볼 수 없다** — 해싱은 단방향이다(PBKDF2-HMAC-SHA256, 210,000회 반복, 워크스페이스에서 재사용한 `scripts/lib/auth.ts` 기준).

## 2. 접근 제어 — 관리자가 몸에 새겨야 할 단 하나의 규칙

**`admin` 역할은 딜 데이터에 대한 자동 접근권을 부여하지 않는다.** 시스템 관리 권한과 딜 조회 권한은 별개다(design 8.10절, 미팅 M7-1). 특정 프로젝트의 데이터를 보려면 관리자도 다른 사용자와 마찬가지로 명시적인 `project_member` grant가 필요하다 — 그 grant 자체도 감사 로그에 남는다. 자신이 멤버가 아닌 프로젝트를 "그냥 확인"하고 싶어지는 순간이 바로 이 규칙이 막으려는 경우다.

## 3. 규제 및 절차 버전 관리

- 진행 중 프로젝트 전반의 `project_policy_pin` 상태 조회.
- 개정이 발효되기 전에 `policy_change` 영향분석 기록을 검토.
- **기록된 `policy_change` 결정 없이 프로젝트가 고정(pin)한 정책 버전을 수동으로 덮어쓰지 말 것** — 이 메커니즘이 규제 개정이 진행 중 프로젝트의 등급을 소리 없이 뒤집는 것을 막는다.

## 4. 마스터 데이터 관리

- `staging_unmapped` 큐 처리 — 매핑되지 않은 산업/회사/단위 코드는 여기서 격리되며 자동 생성되지 않는다.
- 지역·산업 프로필 필드에는 `source`/`verified_on`/`maintainer` 메타데이터가 필수다. `_validate.ts`는 출처 없는 필드를 거부한다. 프로필을 정정하는 관리자는 값만이 아니라 이 메타데이터도 함께 제공해야 한다.

## 5. 알림 및 RAG rule 관리

- RAG 임계값과 히스테리시스 밴드(design 8.2절, 미팅 M3)는 하드코딩이 아니라 설정이다 — 다만 변경에는 즉석 관리자 수정이 아니라 트리거 목록에 따른 ADR이 필요하다.
- 알림 채널 설정, 쿨다운/히스테리시스 파라미터(미팅 M7의 24시간/7일 기본값).

## 6. 데이터 소스 관리

**API 키는 절대 표시되지 않는다** — 관리 콘솔은 키 값이 아니라 존재 여부와 최종 성공 시각만 보여준다. 확정 규칙이며 UI 취향과는 무관하다(design 4.9절).

### 6.1 외부 자료 출처, 키, 승인

외부 자료 출처는 저마다 키가 있어야 하고, 일부는 승인을 받아야 키가 동작합니다. 키는 저장소 맨 위 `.env`에 둡니다(변수 이름은 `.env.sample`을 따르고, 서버가 시작할 때 읽으므로 바꾼 뒤에는 다시 시작합니다). 관리 콘솔 `데이터 소스`(`/admin/data-sources`)는 키가 설정되었는지만 보여 줍니다. 키가 설정되었다고 해서 승인이 있다는 뜻은 아닙니다.

| 출처 | 환경변수 | 신청 위치 | 승인과 걸리는 시간 | 이 출처에 기대는 앱 기능 | 없거나 승인 전일 때 증상 |
|---|---|---|---|---|---|
| DART(금융감독원 오픈API) | `DART_API_KEY` | `opendart.fss.or.kr` 인증키 신청 | 인증키 신청. 걸리는 시간은 저장소에 기록이 없다 | 회사 재무 동기화, 관측 D/E, WACC 화면에서 법정 세율 구간을 고르는 영업이익, 같은 화면에서 가산금리를 고르는 공시 신용등급(화면의 신용등급 수집이 사업보고서와 채무증권 증권신고서를 읽음, 분석가 권한), 회사 프로필·S6 평가 근거 | 회사 동기화가 `503 dart_not_configured`를 돌려 준다. 신용등급 수집은 `503 dart_api_key_missing`을 돌려 주고 WACC 카드는 기본 등급 `BBB-`와 수집 안내를 그대로 보인다. DART 조회는 `DART_API_KEY 미구성`으로 물러나고 재무 값은 `N/A`로 남는다 |
| KRX 데이터 마켓플레이스 OPEN API | `KRX_API_KEY` | `openapi.krx.co.kr` > 마이페이지 > API 인증키 신청, 이어서 서비스별 이용 신청 | 인증키와 서비스마다 관리자 승인이 필요하다. 걸리는 시간은 공개되어 있지 않으니 일찍 신청한다. 베타 수집에는 서비스 여섯 개(`idx/kospi_dd_trd`, `idx/kosdaq_dd_trd`, `sto/stk_bydd_trd`, `sto/ksq_bydd_trd`, `sto/stk_isu_base_info`, `sto/ksq_isu_base_info`)가 필요하다 | 베타 시계열 수집(WACC 화면 `수집 실행`, `scripts/co-newbiz/beta-series.ts`), 예약 작업 `collect.krx` | 키가 없으면 앱 수집이 `503 krx_api_key_missing`. 키는 있는데 서비스 승인이 없으면 실행이 `respCode 401 - Unauthorized API Call`과 관측치 0건으로 실패한다 |
| 한국은행 ECOS | `ECOS_API_KEY` | `ecos.bok.or.kr` > MyPage > 인증키 신청 | 개인 인증키. 공개 시험 키 `sample`은 요청당 10행까지만 되어 운영 수집에는 모자란다. 걸리는 시간은 기록이 없다 | WACC 화면의 무위험이자율·가산금리 참조값(`ECOS 금리 수집 실행`), 예약 작업 `collect.ecos` | `503 ecos_api_key_missing`. WACC 참조값 카드가 무위험이자율과 가산금리를 가져오지 못한 항목으로 알린다 |
| 법제처 국가법령정보 공동활용(`LAW_API_OC`) | `LAW_API_OC`(신청한 OC 아이디이며 비밀 키가 아니다) | `open.law.go.kr` > OPEN API > 활용신청 | `k-law` 스킬 기준 영업일 1~2일 | 법령 목록 동기화(`collect.law`), 에이전트의 법령·조문 확인(`k-law`) | 예약 작업이 `credential_missing`으로 건너뛴다. 에이전트의 법령 확인을 할 수 없다 |

| 금융투자협회(KOFIA) 채권정보센터, `kofiabond.or.kr` | 없음(공개 페이지, 로그인 없음). 스위치 `CO_NEWBIZ_KOFIA_COLLECT` | 신청 절차가 없다. 자동 수집은 **기본 꺼짐**이며 금투협이 허용한다고 **서면으로** 확인해 줄 때까지 꺼 둔다 | 승인 절차가 아니라, 금투협이 등급별 회사채 수익률의 자동 수집을 허용한다는 서면 확인이다(아직 없음. 이 사이트에는 API 계약도, 자동화에 관한 약관 조항도 없다) | WACC 화면의 등급별 신용 가산금리(`spread_basis: kofia_grade`, 칩 "등급별 수익률(금융투자협회)"). ### 6.2 data.go.kr 데이터셋 등록부

`docs/runbooks/data-go-kr-datasets.yaml`은 프로젝트가 쓰거나 쓸 계획인 data.go.kr 데이터셋을 모두 적은 단 하나의 기준 목록입니다. 데이터셋마다 제공 기관, 데이터셋 번호, 엔드포인트, 상태(`in_use` 또는 `planned`), 신청 상태, 승인일, 쓰는 기능, 담당 에이전트를 적습니다.

새 data.go.kr 데이터셋을 쓰기 전에 다음 순서를 따릅니다.

1. **신청.** data.go.kr에서 데이터셋의 `openapi.do` 쪽을 열고 활용신청을 누릅니다.
2. **등록.** 코드를 더하는 같은 풀 리퀘스트에서 등록부에 상태 `planned`, 신청 상태 `pending`으로 올립니다.
3. **구현.** 승인이 나온 뒤 코드를 쓰고, 상태를 `in_use`, 신청 상태를 `approved`로 바꾸고 승인일을 적습니다.

코드나 스킬이 등록부에 없는 `apis.data.go.kr` 엔드포인트를 가리키면 `tests/unit/data-go-kr-registry.test.ts`가 실패합니다.

등록부는 신청 상태를 기록할 뿐 포털에서 읽어 오지는 못합니다. 마지막 대조는 2026-11-26 data.go.kr 마이페이지 > 활용신청 현황이며, 신청 아홉 건이 모두 승인이고 대기·반려·만료는 없으며 모두 **개발계정**입니다. 데이터셋마다 `application_status`는 시스템이 확인한 사실이 아니라 기록한 진술이므로, 등록부를 고칠 때마다 포털에서 확인하고 다른 곳은 고칩니다. 금융위원회 채권 데이터셋 둘(`금융위원회_채권기본정보`, `금융위원회_채권시세정보`)은 2026-11-27에 `in_use`가 되었습니다(ADR-0208 4단계). 엔드포인트와 응답 필드는 등록부에 적었고 저장소 키로 실제 호출해 확인했으며, 교차 확인 화면에만 쓰입니다.

**만료.** 승인마다 기한(`expires_on`)이 있습니다. **2028-09-03**(관세청 데이터셋)과 **2028-11-26**(`금융위원회_채권기본정보`, `금융위원회_채권시세정보`) 전에 data.go.kr에서 활용연장으로 갱신합니다. `국세청_사업자등록정보 진위확인 및 상태조회 서비스`는 포털에 기한이 보이지 않으니 확인합니다. 기한이 지나면 그 데이터셋은 다시 403을 돌려 줍니다. 개발계정은 호출량 상한도 있으니, 정기적으로 호출하는 기능을 열기 전에 운영계정(포털 심사)으로 옮깁니다.

## 7. 로그와 감사

- 감사 로그는 **append-only** — 관리자라도 항목을 삭제할 수 없다. 보존/아카이빙이 유일하게 허용된 수명주기 조치다.
- 컴플라이언스 리포팅용 CSV 내보내기를 제공한다.
