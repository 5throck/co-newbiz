# ADR-0160 — Greenfield S9 plan verification and S10 establishment structure by sub-track

- Status: Proposed
- Date: 2026-10-11
- Deciders: Human reviewer (pending). Drafted by process-governance-manager. AI review alone cannot accept this ADR (procedure, checklist applicability and kill-criteria change).
- Design of record: `docs/designs/2026-10-11-greenfield-dd-and-investment-structure-by-subtrack-design.md`
- Related: ADR-0045, ADR-0047, ADR-0052, ADR-0074, ADR-0099, ADR-0104, ADR-0157, ADR-0159, Wave F-8

## Context

`procedures/_shared/greenfield-dd` is site-centric (site visit, talent pipeline, community acceptance, wastewater kill criterion) and applies to every greenfield project, including the `existing_business_rbd` and `intra_venture` sub-tracks where no new site exists. The greenfield mapping in `SUB_TRACK_DD_CHECKLISTS` is dead because `subTrackChecklistIds()` only serves brownfield. S10 (`deal-structuring`, `brownfield-agent`, M&A inputs) has no greenfield content: establishment vehicle, funding sources, capex tranches, incentives.

The confirmed greenfield sub-track values are exactly: null (plain new site), `existing_business_rbd`, `intra_venture`. `partnership` and the other values are brownfield sub-tracks.

## Decision

1. Keep procedure ids `greenfield-dd` (gate DD, applicability mandatory) and `deal-structuring`; no new procedure ids. `greenfield-dd` 1.0.0 -> 1.1.0 adds sub-track-conditional steps (6 core-team readiness via the `org-readiness-assessment` artifact, 7 technology and market plan verification, 8 entity readiness for `intra_venture`); `deal-structuring` 1.0.0 -> 1.1.0 adds greenfield steps 4-7.
2. Greenfield S9 checklist selection by sub-track: null keeps today's `greenfield-dd` behaviour exactly (Q3); `existing_business_rbd` adds `chk-rbd-technology-checklist`; `intra_venture` adds rbd-technology and entity-formation ef-01/ef-03/ef-07 (read as plan evidence; execution stays in S11). Site steps (1, 3) and site checklists apply only when `site_required` is true. No new checklist item ids; no `gf-13` (Q4).
3. `site_required` is a human-confirmed fact stored in the S9 `process_run.meta_json` (`s9_scope.site_required`, `rationale`, `confirmed_by`, `confirmed_at`). Defaults: null sub-track -> true; `existing_business_rbd` and `intra_venture` have **no default** — a human must always confirm it (Q5; the `intra_venture` default of false was removed by the addendum review).
4. Unknown sub-track on a greenfield route (including a brownfield value) is not blocked: the site-based (null) default applies and a warning is surfaced (Q2).
5. Controls preserved: gate `dd` and its completion criterion; waiver mechanism; binding items unmet under `na`/`waived`; the DD-to-valuation-bridge kill criterion applies to every sub-track; the wastewater kill criterion is scoped to `site_required == true`, not deleted. Sub-track-driven `na` requires a reason; excluded items are shown with the rule that excluded them.
6. Machine-evaluable scope: S10 track split uses `applies_when` on the seeded routing var `project.case_type`. Sub-track and `site_required` conditions are **not** machine `applies_when` predicates, because neither is a seeded routing var in `db/migrations/0014_routing_vars.sql` (the only legal vocabulary enforced by `procedures/_validate.ts`) and this ADR adds no migration. They are stated in the procedure text and enforced by the S9 selection code (Row 2). The wastewater registry predicate counts sites with an unmitigated insufficient assessment, so it cannot trip when no site is in scope.
7. S10 greenfield steps: establishment vehicle (greenfield-agent), funding sources incl. project finance, government funds and subsidies, and lease versus build (financing-agent), phased capex tranches and release conditions (greenfield-agent with valuation-agent; rbd-15 for R&BD), incentives with clawback conditions (incentive-agent). ADR-0045 four axes and sources = uses > 0 stay shared. M&A-only inputs are hidden and stored null for greenfield. Brownfield behaviour is byte-identical.
8. No DB migration (Q7). Greenfield S10 extras live in financing-plan rows, the four-axis evidence artifact and S10 `process_run.meta_json` (`s10_greenfield`); typed columns would need a separate ADR.
9. Grandfathering (Q8): projects whose earliest `project_policy_pin` predates the cut-off constant `GF_SUBTRACK_PREDICATE_DATE` (the merge date of this change; same pattern as `WAVE_F_PREDICATE_DATE`) keep the `greenfield-dd` 1.0.0 selection, unless a human opts the project in through a recorded pin migration carrying a `migration_note`. Opt-in never deletes item state; no completed S9 is reopened; no gate result changes retroactively.
10. Greenfield-facing S9/S10 labels use "plan verification" / "establishment structure" wording, marked **INTERIM-WORDING** (Q1); glossary-curator and the human finalize the terms. No other product terms are coined.
11. flow.spec: **deferred.** The design's v2.7.0 change (new `establishment-structure-hypothesis` activity for greenfield, `deal-structure-hypothesis` narrowed to brownfield) needs activity-level `applicableTracks`, which the flow.spec schema does not support (activities carry only `id`, `agent`, `skills`, `procedure`). flow.spec stays at 2.6.0 until a separate schema change is approved (see follow-ups).

## Policy impact (in-flight projects)

- Known in-flight greenfield project: PRJ-DSE4PW (`01M1MXQN21DP8KYHNW3GDSE4PW`), sub-track `existing_business_rbd`, currently at S8. It has not reached S9, so there is no DD item state to invalidate. Under rule 9 it is grandfathered by default; if a human opts it in (recommended, since its sub-track is the triggering case), the pin migration must record a `migration_note`, and `site_required` must be confirmed by a human before S9 opens (no default for this sub-track).
- The full in-flight list must still be confirmed read-only by Row 2 (query in the design §8) before acceptance.

## Consequences

- R&BD and venture greenfield projects are judged on evidence that applies to them, without silent drops.
- Risk: a lighter procedure may be selected to avoid site scrutiny; mitigated by the human-confirmed, audited `site_required` decision (no default for `existing_business_rbd`) and by keeping the bridge kill criterion universal.

## Addendum (2026-10-12) — DB migration decided

Status stays **Proposed**. The human reviewer reversed the earlier "no migration" choice (Decision items 6 and 8, Q7). Recorded change, implemented as migration `db/migrations/0136_greenfield_subtrack_vars.sql` (`@reversible`, additive only):

1. **Routing vars seeded** (same conventions as 0014; fixed-literal `created_at`, no data defaults):
   - `project.sub_track` — `column`, read off the current `route_decision` row (`is_current = 1`) of the project's source opportunity. A route with a NULL sub-track resolves to `'none'` (decided plain new-site case); no current route stays UNASSESSED (fail-closed: every step applies).
   - `project.site_required` — `asserted`, `requires_evidence_ref = 1`, read only when the `dimension_input` row is live AND reviewed. Confirmed by one person and reviewed by a different person through the human-only `POST /api/projects/:id/greenfield-scope` route. *(Superseded 2026-10-12 by addendum (d): single-person confirmation, no evidence reference, migration 0138.)* This replaces the S9 `process_run.meta_json` (`s9_scope`) storage in Decision item 3.
2. **Machine applies_when**: `greenfield-dd` steps 1, 2, 3, 6, 7, 8 now carry predicates over the two vars (step ids unchanged). The null sub-track evaluates to exactly the v1.0.0 step set (1-5); an unknown or brownfield value on a greenfield route takes the null-sub-track result and the selection code surfaces a warning (never a block); neither `existing_business_rbd` nor `intra_venture` has a default, so their site steps apply (fail-closed) until a person confirms (the earlier `intra_venture` default of no site was removed). `procedures/_validate.ts` accepts var_keys seeded by 0014 and 0136. Decision item 6's "not machine predicates" text is superseded for these steps; the wastewater kill-criterion record is unchanged.
3. **`capex_tranche` table** (project, tranche number, amount, ISO-4217 currency, release condition, status `planned`/`released`/`withheld`, source stage, created/updated/status-change stamps, soft retire). Written only through the human-only `POST /api/projects/:id/capex-tranches` route; released tranches are immutable. Release is two-person: the first `released` call records a release request (audit `capex_tranche.release_requested` with the requester's reason); while it is pending the tranche cannot be edited (409 `release_pending`), and the approver must differ from the creator, the requester and anyone who edited the tranche since the request (409 `second_person_required`). Update audit entries carry before/after amount, currency and release condition (security review 2026-10-12). This replaces the "financing-plan uses rows / `s10_greenfield` meta" storage in Decision items 7-8 for tranches; funding sources stay financing-plan rows. ADR-0161's "new tranche table: deferred" is answered by this table.
4. **Selection and validation code** (Row 2): `GF_SUBTRACK_PREDICATE_DATE` cut-off with the recorded opt-in (`opt_in` action re-pins `shared-greenfield-dd` to 1.1.0 and audits the `migration_note`, `policy_pin_migrated`); `na` on a sub-track-ruled checklist requires a reason; S10 refuses `asset_or_stock`, `instrument_mix` and a non-JV `stake_type` on greenfield, brownfield validation unchanged.

Rollback: the header of 0136 lists the manual rollback SQL (legal while no `dimension_input` row references the two var_keys); the code rollback reverts the procedure predicates in the same PR.

## Addendum (2026-10-12, d) — site_required: single-person confirmation, no evidence reference

Status stays **Proposed**. **User decision, recorded in chat on 2026-10-12** (human acceptance of this change; the ADR as a whole still needs the human final approval above).

- **Decision.** The S9 `project.site_required` confirmation takes effect **without a second person's review**, and the **evidence reference is no longer collected**. `POST /api/projects/:id/greenfield-scope` takes `{site_required: boolean, rationale: string}` (`rationale` mandatory, non-empty). A client that still sends `evidence_ref` is not rejected; the field is ignored. The `review_site_required` action is removed.
- **Effect.** The person who confirms also records the review in the same transaction (`dimension_input.reviewed_by = asserted_by`), so the value drives routing and S9 scope immediately (response `site.basis = confirmed`; `pending_assertion` is always `null`). Re-confirming supersedes the live row as before. The audit log carries `dimension_input_single_person_confirmation` with `single_person_confirmation` and the rationale. `db/lib/applies-when.ts` is unchanged (it still reads live AND reviewed rows).
- **Scope of the relaxation.** Implemented as a narrowly scoped repository path, `assertWithSinglePersonConfirmation` in `db/repositories/dimension-input.repository.ts`, with an allowlist containing only `project.site_required`. Every other `dimension_input` variable keeps the cross-person review rule (`review()` still refuses `reviewed_by = asserted_by`). The route stays human-only (cookie session + CSRF, `analyst`+, membership, insider status on MNPI projects).
- **Migration 0138** (`db/migrations/0138_site_required_no_evidence_ref.sql`, `@reversible`): `UPDATE evidence_var SET requires_evidence_ref = 0 WHERE var_key = 'project.site_required'`. Migration 0136 is not edited. Rows written under 0138 store `evidence_ref = ''` (column stays NOT NULL); a rollback restores the flag for new assertions only.
- **Rationale (user).** Site applicability is a factual scoping call made by the deal analyst; a second-person review and a citation added friction without a matching control benefit, and the earlier fail-closed state kept site steps applied for projects that plainly have no site.
- **Acknowledged weakening.** This deliberately weakens the two-person review (assert by one person, review by another) and the mandatory evidence citation that addendum (a) adopted following the security-review L1/M1-era recommendations. Residual risk: one person can now remove the site steps (1, 3) and the site checklist items from S9 scope alone, and no citation backs the call. Mitigations kept: human-only route, mandatory rationale, audit entry naming the single-person confirmation, supersede history, and the wastewater kill criterion still scoped to `site_required == true`. Gate approval remains a human act (boundary #2).
