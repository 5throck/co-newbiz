## Overview

co-newbiz is an AI-agent team and system that owns and operates the policies, procedures, guidelines, and checklists for new-business review — **Green Field** (new establishment) and **Brown Field** (M&A, including R&BD as a Brown Field subtype) — and implements that governance as a working review system, rather than a static document set.

Two axes are co-equal, per the design's own framing: **(A) governance ownership and operation** (authoring/amending policies, procedures, guidelines, checklists, and running their standing operation — compliance monitoring, waivers, interpretation registry, KPIs) and **(B) system build and maintenance** (implementing A as a system and keeping it running). A third axis, **(C) deal review**, runs real reviews on top of A and B and is the quality check on both.

Distinctive to the domain: many target industries have no direct market data, so demand is estimated through a proxy chain across upstream industries (e.g. crankshaft → marine engine → ship, with CGT/BHP/ton unit conversion). Chain reliability caps the confidence of every downstream conclusion — this is the RAG framework's data-confidence cap rule (see `docs/governance/rag-framework.md`).

**Tech stack**: SQLite (`bun:sqlite` access layer retained; Prisma + `@prisma/adapter-better-sqlite3` for schema/typegen) · Next.js (App Router, Route Handlers) + Prisma + Tailwind CSS + Recharts — superseded the original Hono + React/Vite + ECharts stack per ADR-0069/0070 (accepted 2026-08-26) · Python (python-docx / reportlab / python-hwpx) for document rendering · MCP server over stdio, REST-proxied · TypeScript CLI (`bun scripts/co-newbiz/newbiz.ts`).

## Agents

**41 agents** across four co-equal domains plus `_core` and `_shared`, coordinated by PM acting as New Business Review Lead. Domain leads are design/review owners, not dispatchers — the workspace flat PM Gateway is preserved in full (PM is the only agent users invoke directly; all 40 specialists require PM dispatch).

| Domain | Count | Lead | Concern |
|---|---|---|---|
| `_core` | 1 | `pm` | Coordinates the four domain leads, enforces stage gates, approves ADRs |

Full roster with per-agent tier and role: `AGENTS.md`. Full definitions: `agents/*.md`.

**Three-stage review** applies to every deliverable: AI 1st (formal/completeness) → AI 2nd (cross-domain — must come from a different domain than the author) → human final (judgement and approval). Regulations, gate approvals, investment decisions, the security/privacy model, and ADRs cannot pass on AI review alone.

## Domain Configuration

- **RAG signal system** (`docs/governance/rag-framework.md`): six dimensions (financial, market, data confidence, regulatory/permit, technical/execution, risk) plus overall, rule-based (not weighted-average) — a Kill Criteria trigger or any assessed Red dimension forces overall Red immediately; an incomplete assessment (fewer than six dimensions genuinely assessed, none Red) yields no overall grade rather than defaulting to a color (Wave 5.10 defect fix, see `docs/pilots/pilot-001-system-rerun.md`).
- **Stage gates**: Screening → Pre-FS → FS → DD → Entity IC → Group IC, with Entity IC approval required before Group-level procedure entry (`approval_chain`, ADR-0028). Numbered lifecycle phases (0 intake → 1 Screening → 2 Pre-FS → 3 FS → 4 DD → 5 IC → 6 execution & post-close → 7 finalization/QA) are defined in `docs/phase-definitions.md` and referenced by the skill graph's `phase` edges (ADR-0073).
- **Governance layers** (`docs/governance/governance-operations.md`): Policy / Procedure / Guideline / Checklist / Template, each with distinct enforceability and revision authority — see the document-layer table in the design.
- **Procedure inheritance**: `procedures/{_shared,entities/<company>,regions/<ISO2>,group}/<proc>/schema.yaml` — entity/region procedures reference shared procedures via `references:` + `overrides:`, never copy them (ADR-0020); copies are audit-detected and blocked.
- **Information protection** (`docs/information-protection.md`, `docs/security/security-model.md`): project-membership access control (deny-by-default), minimal-collection/aggregate-only handling of personal data (executive compensation, comp benchmarks), and MNPI insider-list/access-log handling for listed-company deals — none of this is deferrable to a later phase (ADR-0038/0039/0040).
- **Investment vehicle structuring** (ADR-0045, `skills/investment-vehicle-structuring/`): tax structure, liability isolation, financing leverage, and exit structure are mandatory Pre-FS deal-structure-hypothesis axes for both Brown Field and Green Field, enforced via `checklists/brownfield-feasibility-checklist.yaml` bf-12 / `checklists/greenfield-feasibility-checklist.yaml` gf-11.
- **Remaining known gaps** (as of 2026-08-21): the 24 documented-but-unmigrated DB tables gap was closed via `db/migrations/0011_dd_finding_and_remaining_tables.sql` (all 68 documented tables now migrate cleanly); Wave 5.7B then wired the plain membership-filtered read/write surface over them — REST `app/server/analysis.ts` + `deal-review.ts`, MCP `tools/analysis.ts` + `tools/deal-review.ts`, plus `docs/architecture/openapi.yaml` with its executable drift gate (`tests/unit/openapi.test.ts`), closing the api-spec/mcp-integration Status gaps. The engine-1 run-versioning wave then landed ADR-0005's engine half: `db/lib/versioning.ts` (createRun snapshot + input_hash + diffRuns bridge), the `model`/`diff` CLI cases (`scripts/co-newbiz/model.ts`), the runs REST surface in `app/server/analysis.ts`, and the `compare_runs` MCP tool. The engine-2 simulations wave then exposed ADR-0026's Monte Carlo engine over REST: `db/lib/simulation.ts` composes the scenario from a run's `sim.*` inputs plus the project's `contingent_liability` rows, spawns `python/monte_carlo.py` with an args array (never shell), persists `simulation` + `simulation_result` (quantiles only — `simulation_draw` stays empty because the engine emits no per-iteration draws), and `POST /api/simulations` / `GET /api/simulations/:id/results` + the `run_simulation`✱ MCP tool sit on top (29 catalog tools live). NPV-level diff decomposition and `run_model` stay deferred until a valuation engine exists — v1 versions inputs, it does not value them. The remaining engine-dependent surface (financial analysis, projections, proxy chains, reports) stays deferred to the CLI-backed job surface. `industry-profiles/` gained its schema contract (`_schema.yaml`/`_validate.ts`, mirroring `region-profiles/`) but has zero populated profiles — populating one requires genuine cited industry research per KSIC code, which cannot be fabricated (`admin-console-operations` was checked and found to already accurately self-document its 3/10-built state — no fix needed there). Still open, larger scope: `newbiz.ts`'s 9 undeveloped CLI commands (`fetch`, `md:sync`, `law:sync`, `policy:sync`, `policy:impact`, `fin:project`, `calibrate`, `convert`, `export` — deliberately not stubbed per the CLI's own module comment; `model` and `diff` landed with engine-1, and `assume`/`glossary:lint`/`adr:new` landed with the 2026-08-21 CLI batch wave via `scripts/co-newbiz/{assume,glossary-lint,adr-new}.ts`, with the REST `POST /api/assumptions` and the `assume` CLI now sharing one validation+insert path, `db/lib/assumption.ts`), `market-data-pipeline` fetch, `deal-workspace-operations`'s closure/archival logic, and `hwp-document-processing`'s extraction path (generation only is ported so far). The 2026-08-21 badge/provenance wave enriched `GET /api/projects` list rows with `rag_overall`/`rag_assessed_at` (latest overall-grade `rag_assessment` per project, one aggregate query) and gave the envelope first-class FR-SYS-03 provenance meta (`app/server/envelope.ts` `provenance()`), populated on observations (`meta.source` when all returned rows share one source) and dd-finding POST (run linkage to the latest registry row for the key); two client-gated gaps remain open by design: a list-row `stale` signal (not derivable today — `fact_market_observation` carries no project binding and `ttl_days` is per (run, assumption_key); needs either project-bound freshness data or a design-defined staleness rule) and notification read/unread (`notification` has no `read_at` and no cleanly-fitting column exists in `session`/`app_user` — `watch.last_checked_at` is a change-detection watermark, not a read state — so it requires a migration).

## Investment & Valuation SSOT (2026-10-16)

Governing records and settled principles for the Green Field S5-S8 investment and valuation chain. Cross-references only — the ADRs are the authority; do not duplicate their content.

- **Governance records**: ADR-0174 (`docs/adr/0174-total-investment-and-s8-handoff.md` — investment plan hand-off), ADR-0176 (`docs/adr/0176-investment-simulation-and-s8-evaluation.md` — S5 investment simulation + run storage), ADR-0178 (`docs/adr/0178-s8-valuation-pnl-volatility-prelaunch.md` — S8 valuation, S5 single source + pinned reference, `s5_pnl`).
- **Green Field S5-S8 principle**: S5 is the single source of the investment plan; S8 reads it through a versioned pinned reference (`s5_plan_pin`) with `재평가 필요` staleness and human-only re-pin/revert. Direct S8 line edits must not diverge from S5 (editor scope under review 2026-10-16).
- **Basis vocabulary**: `비율 추정` (fallback), `S5 투자 계획` (unified; the legacy capex-only value is labelled `예전`), `s5_pnl` (in implementation).
- **Human-only acts** (decision-support boundary): investment-simulation 가정 확정 (`investment_simulation.confirmed`), 최신 S5로 갱신 (`s5_plan_pin.repinned`), 복사본으로 되돌리기 (disconnect).
- **Known issues**: copy-path period alias (`월`) mis-annualization pending fix (the pinned path is correct); S5 default draws 2,000 decided 2026-10-16, pending implementation (ADR-0176 Amendment 2026-10-16); market-scope compatibility + IRR-ceiling guard accepted as ADR-0179 (`docs/adr/0179-market-anchor-scope-compatibility.md`), pending implementation.
